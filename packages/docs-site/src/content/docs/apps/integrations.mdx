---
title: Integrations
description: Maintained, validated site-wide tags for analytics, advertising, marketing, and support providers.
---

- **Type:** Integration module
- **Build impact:** Injects configured provider tags
- **Consent:** Uses Typeroll's existing consent categories

Integrations replaces pasted third-party snippets with maintained platform
code around validated provider identifiers. A malformed identifier is dropped
instead of being embedded into the site. When a provider changes its standard
tag, Typeroll can update the shared implementation centrally.

## Supported providers

| Group       | Providers                                                                                                                   |
| ----------- | --------------------------------------------------------------------------------------------------------------------------- |
| Analytics   | Google Analytics 4, Google Tag Manager, Hotjar, Microsoft Clarity, Plausible, Fathom Analytics, Matomo                      |
| Advertising | Meta Pixel, LinkedIn Insight Tag, TikTok Pixel, Pinterest Tag, Snap Pixel, Reddit Pixel, X Pixel, Microsoft Advertising UET |
| Marketing   | HubSpot, Mailchimp Connected Site                                                                                           |
| Support     | Intercom, Crisp Chat, Tawk.to                                                                                               |

Each provider declares its identifier fields, validation pattern, placement,
and consent category. Client identifiers are public by design because the
provider's browser tag needs them; they are not treated as server secrets.

## Consent behavior

Providers declare the categories `necessary`, `functional`, `analytics`, and
`marketing`. The cookie banner today asks one question: a visitor accepts all
cookies (`all`), only necessary ones (`necessary`) or rejects them (`rejected`).
Every non-necessary tag stays inert until the visitor accepts all; it does not
yet distinguish analytics from marketing. Google Tag Manager is in the
marketing category because a container may load advertising tags.

## Form conversions

With Meta Pixel, Google Analytics 4 or Google Tag Manager set up here, a
successful form submission sends one conversion event, with no script of your
own:

| Provider | Call |
| --- | --- |
| Meta Pixel | `fbq('track', <event>, params, { eventID })` |
| GA4 | `gtag('event', <event>, { ...params, event_id })` |
| Google Tag Manager | `dataLayer.push({ event: 'typeroll_conversion', typeroll_conversion: { ...params, event_id, meta_event, ga4_event } })` |

**Which event.** A Recurring Events registration for a date sends
`CompleteRegistration` / `sign_up`, and an interest-only sign-up sends `Lead` /
`generate_lead`. Each Series can choose "Lead for both" or none. Any other form
sends what its `conversion` setting names: `meta_event` (`Lead`,
`CompleteRegistration`, `Contact`, `Schedule`, `SubmitApplication`, `Subscribe`,
`StartTrial`), `ga4_event` (`generate_lead`, `sign_up`, `contact`, `schedule`,
`submit_application`, `subscribe`, `start_trial`) and an optional
`content_name`. Set it with `update_form`.

**Parameters.** `event_id`, `form_id`, `content_name`, and for Recurring Events
`series_id`, `occurrence_id` and `interest_only`, plus the campaign values
`utm_source`, `utm_medium`, `utm_campaign`, `utm_content` and `utm_term`.
Names, email addresses, companies and other answers are never sent.

**Once per submission.** `event_id` is `tr_` plus the submission id. A retried
submission keeps it, and two real sign-ups in one visit get two ids and two
events. Nothing fires for a failed submission, a full or closed date, or a
validation error.

**When it is on.** By default from render version 20. The setting
`form_conversions` is `auto` (the default), `on` (any render version) or `off`.
The page carries `<html data-tr-conversions>` while it is on.

**Moving from a script of your own.** Remove any script in `scripts_body_end`
(or elsewhere) that fires a conversion on `typeroll:form-success`, in the same
publication that turns form conversions on, or every sign-up counts twice.

### What fires under each cookie choice

| Choice at submit | In the browser | Conversions API (if set up) |
| --- | --- | --- |
| No cookie banner on the site | Fires at once | Sent with `fbp`/`fbc`, IP and user agent |
| `all` | Fires at once | Sent with `fbp`/`fbc`, IP and user agent |
| Not chosen yet, `necessary` or `rejected` | Waits in memory; fires once if the visitor accepts all on the same page view | Sent only with email matching on, with the hashed email alone |
| The visitor leaves, reloads or is redirected before accepting | Never fires | As above |

The runtime listens for `typeroll:consent-activated`, which the cookie banner
dispatches after it has started the gated tags. Every outcome is also
announced as a `typeroll:conversion` event on `document` (event id, event names,
consent state, what was sent and whether it waits), which a site script or test
can read. Nothing is stored in the browser.

### Campaign values

Every form submission posts the page's `utm_*` parameters. Without them it
posts the Attribution app's last-touch values, and failing that its first-touch
cookie values. The submission keeps them as `attribution`, and app actions such
as Recurring Events receive them, so no hidden fields are needed. Meta's
`_fbp` and `_fbc` cookies (or an `fbc` built from `?fbclid=`) are posted only
when the visitor has accepted all cookies, or the site has no banner.

### Meta Conversions API (optional)

Turn it on with **Meta Conversions API — access token** (encrypted, never
shown again and never published to the site). After a submission is saved, and
its app action has completed (a Recurring Events registration exists), the
server sends the same event name and `event_id` to Meta, so Meta counts the
conversion once. The event has `action_source: website` and the page address
without its query string. It is sent once per submission.

**Match by email** is a separate switch, off by default. When it is on, the
server also sends the SHA-256 hash of the email address, normalized to lower
case, for visitors who did not accept cookies too. It needs a notice of at
least 20 characters, which forms with an email field show above the submit
button. Without the notice on the page, nothing is matched. Whether you may do
this without cookie consent is your decision as the site owner.

### Checking it

- `send_test_conversion` (or `POST /api/v1/sites/{site}/integrations/conversions/test`)
  sends one synthetic event with **Meta Conversions API — test event code**. It
  then shows under Events Manager → Test events. It creates no submission and
  no registration.
- `read_conversion_status` (or `GET .../integrations/conversions`) lists the
  last 50 outcomes. Each entry names the form, the event and its id, and the
  cookie choice at submit. It also says what the browser does for that choice
  (`fires`, `waits_for_consent`, `not_configured`) and what the server sent
  (`sent`, `skipped` with a reason, `failed` with Meta's message, `off`). It
  holds no contact data. Whether the browser actually fired is not reported
  back.
- Headless browsers that expose `navigator.webdriver` (Playwright, Puppeteer)
  make the Meta Pixel send nothing, even though `fbq` is called. In a test,
  check the `fbq` call or the `typeroll:conversion` event, not Events
  Manager.

## Scope

This module owns site-wide tags placed in the document head or at the end of the
body. A widget or embed placed at a particular point in page content belongs in
a block, not in this catalog.
