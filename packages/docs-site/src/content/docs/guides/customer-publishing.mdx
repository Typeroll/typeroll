---
title: Publishing with your own accounts
description: Connect GitHub, Cloudflare, domains and media once per organization, then publish static sites from Typeroll.
---

This workflow applies to Typeroll Cloud and self-hosted installations with
customer publishing enabled. Cloud users connect their own accounts; Typeroll
operates the publisher authorization service. Self-hosting operators must first
configure the publisher Apps, OAuth and private draft storage for their portal.
See [Cloud and self-hosting](../../getting-started/cloud-and-self-hosting/).

## Start editing before connecting accounts

You can create sites, connect an AI agent, edit pages, save drafts and share an
expiring preview before setting up publishing. With customer publishing enabled,
new uploads use the hosting operator's private draft storage until your R2 access
is ready. Public deployment stays locked and links to **Publishing** with the
missing setup steps. A public website address appears after the exact deployment
has been verified at that address.

Your hosting operator must enable customer publishing and configure private draft
storage. Existing managed sites retain their existing publishing mode until they
are explicitly migrated.

## Publishing setup checks

Starting with Core 0.1.99, both the site overview and editor check Publishing
before enabling deployment. The check includes GitHub, the site's Hosting Group,
the selected version's website address, required media storage and hosts, and the
selected build engine's completed verification and required capabilities. An
older build engine can need an update even if its previous setup succeeded.
Select the listed **Publishing → Builds** link and finish build setup to update
and verify it.

Deployment stays disabled while the check runs or cannot be completed. Missing
steps link directly to their settings. Return after correcting them, or select
**Check again** after a check error. The server checks again before accepting a
job, including deployments requested through the public API and MCP.

Saved publication status still determines which pages enter the next build; it
does not make a page live. Editing, saving and Preview remain available. A new
custom domain may be prepared before traffic DNS is switched: the candidate must
still be built and verified before cutover. External service failures can still
interrupt a build after these setup checks pass.

## Storage before importing

Starting with Core 0.1.95, importing a website, external media, a sitemap or Search
Console data requires the organization’s own verified storage. Select
**Publishing → Media storage** to connect it before starting an import. This
requirement applies in the UI, public import API and MCP; imports never fall back
to the operator’s draft bucket. GitHub and website domains can be connected later.

Typeroll automatically provisions a media transfer Worker in the organization’s
Cloudflare account. The **Media transfers** status shows readiness or an actionable
setup error. Existing OAuth connections may show **Allow media transfers in
Cloudflare**; approve that permission once. No replacement R2 keys or GitHub build
connection is needed. Source files travel directly to customer storage and are
verified there, regardless of the selected build provider.

## Organization setup

Open the sidebar, select the correct **Organization**, then select **Publishing**
under **Account**. On mobile, open the menu first. Organization owners and admins
manage these connections.

1. Select **Connect GitHub**, sign in to your personal account or as an owner of your GitHub organization,
   and authorize Typeroll. If the App is missing, the GitHub card shows the orange
   **Setup incomplete · Install the GitHub App** step. Select **Install and connect
   GitHub**, choose the account that will own your repositories, select **All
   repositories**, and approve the installation. Typeroll returns automatically
   to verify access. Choose an account if more than one is available. The card
   confirms **Connected** when all checks pass; signing in alone is not completion.
   No account name or ID needs to be typed.
2. Select **Connect Cloudflare**, sign in and approve the account. Optional DNS
   and URL rewrite permissions let Typeroll configure domains automatically.
   You can decline these and let your administrator or AI agent manage DNS.
3. Typeroll checks R2 automatically. If activation is required, follow the
   account link to **Storage & databases → R2 object storage → Overview** and
   complete Cloudflare's subscription checkout. Return and select
   **I’ve activated R2 — check again**. Typeroll creates separate private-original
   and public-media buckets and configures browser uploads.
4. In **R2 object storage → Overview → Account Details → Manage API Tokens**,
   create an **Account API token** with **Object Read & Write** for **both buckets
   shown in Typeroll**. Enter its **Access Key ID** and **Secret Access Key**, then
   select **Verify keys and finish setup**. These are different from the API token
   value. A Super Administrator can create account tokens; a User API token is an
   alternative whose access depends on that user's continued membership.
5. In **Builds**, select the organization's build provider and complete its
   shared-engine setup. Cloudflare builds need a one-time builder repository
   connection and build token; GitHub Actions uses the existing Typeroll App
   connection. See [Cloudflare hosting and builds](../../publishing/cloudflare/).
6. Under **Organization domains**, choose a **Cloudflare domain** from the connected
   account. Enter short labels in **Media subdomain** and **Sites subdomain**, such
   as `media` and `sites`. The complete addresses appear below the fields. Select
   **Configure domains** to connect the media hostname to R2 and queue media
   migration. HTTPS activation is checked automatically. Each site and version
   gets its own website address when you publish.

The guided GitHub installation continuation is available in Core 0.1.78 and
later, once your hosting operator deploys that release. Earlier versions require
you to install the publisher App and then select **Connect GitHub** again.
Cloud production and staging use separate publisher Apps: approving one does not
install the other. The required installation step survives reloading Publishing.
If your GitHub organization requires an owner's approval, return after approval
and select **Already installed? Check connection** to verify access.

Starting with Core 0.1.79, **Finish build setup** checks Cloudflare build access
before creating the build project or changing build storage. A connected
Cloudflare account can still need separate permission for **Workers Scripts**
and **Workers Builds**. If the Builds card says **Build permissions required**,
select **Approve build permissions**, approve in Cloudflare, then return and
select **Finish build setup**. Hosting and media remain connected.

Starting with Core 0.1.80, returning from Cloudflare approval automatically
rechecks the Builds card even after the connection card clears the callback
address. If an older error remains on an earlier version, select **Refresh
status**. A stale message does not mean that you need to approve access again.

When a test build finishes, its saved status changes in the background. The
Builds card recovers a conflicting status check by reading the latest result;
it does not start setup or another test build again. On Core 0.1.100 and earlier,
if **Build settings changed. Reload and try again.** remains beside **Running a
test build…**, reload Publishing once to see the saved result. This message
alone does not mean the test build failed or that you need to reconnect accounts.

On older versions, if setup shows HTTP 403, select **Refresh status** first to
show the permission action. If setup fails, it has stopped: the card should show
the failed step and next action, rather than a continuing preparation message.

Starting with Core 0.1.79, the GitHub card always shows two separate steps:
**1. Sign in to GitHub** and **2. Install the GitHub App**. Each has its own status
symbol and text. Approving sign-in makes the first step green; the second stays
orange until the App's repository access is verified. Both stay visible and
green after connection. If a personal account needs renewed authorization,
the first step identifies it without asking you to reinstall the App.

Cloudflare sign-in and R2 upload access are separate. The current OAuth connection
can prepare storage but cannot create the S3 upload key pair. Create the keys
once using **Manage API Tokens** and save them in **Media storage**. After the
upload check succeeds, reuse those keys for the organization's sites; you do
not need to create new keys for each site or reconnect a working account.

Use the refresh icon beside **Cloudflare domain** to retrieve newly added domains. Refreshing keeps the
existing account connection. An empty result does not mean you need to reconnect.
If the saved OAuth grant lacks domain permissions, **Allow domain access** appears.
It opens Cloudflare's approval screen and keeps the existing account and R2 setup.
Typeroll will not replace an existing DNS destination or an existing shared media
hostname through this setup action.

For external DNS or agent-managed settings, open **Manual settings or external
DNS**. Enter the complete **Site address base** and **Shared media host**, choose
**Me or my AI agent**, and save. Read **Setup instructions**, apply the records,
then select **Check domain status**.

Each Hosting Group owns a Cloudflare hosting account and a site address base.
Default is created automatically and reuses the organization connection. One
group is enough to get started; add another only when you need another Cloudflare
hosting account. Its neutral gray card means that no separate setup is needed
here. Configure the shared connection and address base in **Cloudflare account**
and **Domains**. The Organization owns shared media,
DNS access, GitHub and the build-provider selection.
Each site gets its own generated private repository and static Pages project.
Adding a site or version reuses the organization connections.

Account ID is only needed in advanced token setup. In Cloudflare, select the
account and use **Search → Copy account ID**, or **Workers & Pages → Account
Details → Account ID**. Copy the 32-character account value, not a Zone ID.

### Personal GitHub accounts

You can use your personal account for both site repositories and the shared build
repository. It does not need to become a GitHub organization. Typeroll still
manages these connections once per Typeroll Organization.

Typeroll securely stores your authorization to create new repositories and renews
it when needed. Publishing to existing repositories and version branches uses
the App installation. If you revoke authorization or leave it unused for six
months, open **Publishing → GitHub account → Personal account authorization**
and select **Reconnect GitHub**. Existing repositories are kept. No personal
access token needs to be copied into Typeroll.

### Approve a GitHub permission update

An existing connection does not need to be disconnected or connected again.
In **Publishing → GitHub account**, select **Approve GitHub update** when it
appears. This opens the existing installation in your personal account or GitHub organization.
Review and accept the requested permissions as the personal account holder or a GitHub organization owner,
then return to Typeroll. Typeroll checks automatically and confirms when the
permissions are up to date. **Check GitHub permissions** repeats the check.

If Typeroll says it needs to enable GitHub build access first, your hosting
operator must update the publisher App registration before an approval is
available. You do not need to edit an App, create a token or reconnect.
Your existing connection remains active. Permission approval alone does not
change the selected build provider.

### When DNS is hosted elsewhere

R2 media domains must belong to a zone in the same Cloudflare account as the
bucket. You do not need to move your root website, email or unrelated subdomains.
Cloudflare's partial CNAME setup connects selected hostnames while keeping your
existing authoritative DNS provider and nameservers. It requires
Business or Enterprise. Selecting external DNS management in Typeroll means you
or your agent manage the records, including records in Cloudflare; it does not
bypass this provider requirement. If your domain already uses Cloudflare DNS,
keep other records pointing at their existing services.
A CNAME pointing to an `r2.dev` address is unsupported.
See [R2 custom domains](https://developers.cloudflare.com/r2/buckets/public-buckets/)
and [partial setup availability](https://developers.cloudflare.com/dns/zone-setups/partial-setup/).

### Read status and complete setup

**Shared media domain status** distinguishes missing Cloudflare access, unfinished
R2 setup, an unattached or disabled media domain, pending ownership/certificate
activation, and an active Cloudflare media domain. Provider errors are shown as
an unknown status, not as proof that a working domain is disconnected. The panel
names the connected account and public bucket and records when it was checked.

For manual setup, open **Cloudflare → R2 object storage → the public bucket →
Settings → Custom Domains → Add**. Enter the shared media hostname, select
**Continue**, review the record and select **Connect Domain**. Use **Manage DNS**
in the connected domain’s menu to view the record. With partial setup, also apply
Cloudflare’s supplied verification and CNAME records at your DNS provider. The UI
links to Cloudflare’s current instructions; do not guess a target or point the
hostname at the S3 API endpoint.

An active media-domain status does not verify every site address or publish a
site. Website and version addresses have their own DNS requirements and public
verification in the site's Publishing flow. The address base itself does not
serve a website; generated addresses are below it. Deployment verifies actual
published media files before exposing the live link.

The organization API `GET /api/v1/publishing/domains` and MCP
`read_organization_publishing_domains` return the same `domain_status`, including
`state`, `checked_at`, `zone_check`, certificate/ownership state and structured
`steps`. Set `sites_domain` and `media_host` independently using the corresponding
PUT route or `set_organization_publishing_domains`. Legacy `default_domain`
configurations retain their old addresses until explicitly updated. Changing the
site address base affects subsequent deployments; an existing shared media host
cannot be replaced by a plain settings overwrite.

To use the same automatic setup from an agent:

1. Call `GET /api/v1/publishing/zones` or MCP
   `list_organization_publishing_domains` to list available domains.
2. Read the current configuration revision from the domains endpoint.
3. Call `POST /api/v1/publishing/domains` or
   `configure_organization_publishing_domains` with `revision`, `zone_id`,
   `media_subdomain` and `sites_subdomain`. The labels contain no dots or URL.
4. Poll the domains endpoint while `domain_status.state` is `pending`. A
   `setup_error` means settings were saved but provider setup needs attention;
   use the returned revision when retrying.

These endpoints require an organization API key. Site keys cannot discover or
configure organization domains. Setup creates the selected R2 media connection;
it does not publish a website or modify unrelated DNS records.

## Publish a site or version

Choose the site and its **Version**, save changes and select **Deploy**. The
`main` version publishes the live site. Other versions use `version-<version-id>`
Git branches and separate public test addresses under the organization's site address
base. Those versions and default-domain demos use `noindex`.

Typeroll freezes the selected version, including inherited blocks, templates,
content types, templates and runtime settings, and pushes generated source to GitHub.
The selected shared build engine installs the pinned dependencies and runs Astro.
The resulting static files go to the Site’s Hosting Group on Cloudflare Pages. While the build or domain propagation is pending, the interface shows
progress. The link appears automatically after verification.

The repository is generated output. Edit through Typeroll's UI, API or MCP.
Manual repository changes are unsupported and may be replaced by a publication.

### Fast handoff and recovery

Starting with Core 0.2.4, customer publishing separates source capture, the Git
commit and build dispatch into short, resumable steps. Typeroll reads a consistent
view of the selected version and its inherited content, excludes private drafts,
and freezes the public source with its renderer and destination addresses.
Edits saved after this snapshot belong to a later deployment.

The customer’s GitHub or Cloudflare engine resolves website and media addresses,
prepares images, builds the static site and verifies its output. Waiting for that
engine does not keep a CMS request open. Retries reuse the saved snapshot and Git
commit. Leave the page open or return later; UI, API and MCP show the same job.
Do not start a duplicate deployment just because the external build is still running.

Generated repositories keep pages, templates and other content records in
`content/`, indexed by `publication.json`. Unchanged Git files are reused; removed
pages and unsupported manual files are removed from the generated tree. The build
publishes a complete static site, with unchanged HTML reused when the
[partial-build cache](#partial-builds) is available. Images stay in R2, outside Git. The repository contains its frozen
renderer, content, address mappings and integrity manifest, so independent builds
do not fetch mutable content from the CMS.

The CMS still reads and validates the public source before handing it off. Large
sites and provider latency can take longer; this is not a fixed publication-time
guarantee. API/MCP status can include `job.coordinator` with the last completed CMS
checkpoint and its attempt duration. It excludes time waiting for an external
build and is not the site’s total build duration.

For customer publishing, `dry_run` validates and prepares the source without
pushing Git or starting an external build. It does **not** prove that Astro will
build successfully. Other self-hosted deployment adapters may run a local build
without uploading it. Check the job’s phase to see which validation completed.

## Website and media hosts

Open **Site settings → Publishing → Website and media addresses**. Set the
website host and, optionally, a separate media host. For example:

| Setting                        | Example                                                                 |
| ------------------------------ | ----------------------------------------------------------------------- |
| Organization shared media host | `media.example.com`                                                     |
| Site website host              | `www.customer.com`                                                      |
| Site media host                | `images.customer.com`                                                   |
| Media path prefix              | Empty for a separate media host; `/media` when sharing the website host |

Before a site has its own media host, an image can use
`https://media.example.com/media/<site-media-id>/photo.png`. With a separate
site media host it can use `https://images.customer.com/photo.png`. Referenced public media is included in the static site output; shared media
aliases remain available through organization storage and configured URL rules.
No dynamic Worker serves the website or the images.

A media item's `public_path` can preserve a legacy path such as
`/wp-content/uploads/2024/photo.jpg`. Public paths are immutable: a different file
must use a new path. This protects older deployments and cached links.
Organization media URLs and previously published aliases remain available after
a site changes its preferred host. Builds use the new preferred addresses;
images are not moved into GitHub.

## Prepare a domain change before switching traffic

1. Save the future website and media addresses. This records intent and keeps
   the current website address active.
2. Select **Prepare domain change from published content**. The candidate uses
   the last successful public snapshot, including its renderer, rather than
   newer saved CMS edits. Internal absolute links on the old website origin,
   canonicals, sitemap addresses and media references are retargeted.
3. Review **Domain verification**. Apply any validation records shown if you
   manage DNS externally. For Cloudflare DNS, use **your domain → DNS → Records**.
   Refresh verification or wait for its automatic update.
4. When the candidate and certificate checks permit it, select **Switch website
   traffic**. With external DNS management, apply the reviewed CNAME yourself.
   Version custom domains require a **proxied** Cloudflare CNAME.
5. Typeroll checks the public address before marking it live.

Cloudflare Pages may require traffic DNS to validate a hostname. Typeroll does
not overwrite an existing destination while its certificate is unverified. If
validation cannot finish with current DNS, the change stays blocked and needs a
provider-specific migration arrangement; it is not a promise of a zero-downtime
cutover for every external DNS setup. Reviewed DNS changes also stop if another
administrator changed the records in the meantime.

## Media migration and independent builds

After R2 and the organization shared media host are connected, Typeroll copies old
originals to your private bucket, verifies SHA-256 hashes, and changes storage
references only after verification. The transfer starts automatically and continues
in the background, including libraries with thousands of images. You can close
the browser. **Publishing → Media storage** shows verified copies and updates
automatically; temporary interruptions are retried without starting over. Concurrent edits and uploads granted before
connection are handled without switching them to an unverified destination.
Progress and retry instructions appear in Publishing. Existing source files are
retained while older publications may still need them.

### Large libraries and first publication

Original transfer and publication preparation are separate steps. The background
transfer moves the library into private R2 storage. A publication prepares only
media referenced by its frozen content and any retained published versions.

Core 0.1.94 includes background preparation after uploads and imports, using the
Organization's selected Cloudflare or GitHub build engine. **Media** shows the
progress and offers **Retry preparation** if a job stops. Setup can happen later:
you can upload, import and edit before connecting a build provider. Preparation
waits until **Publishing → Media storage** and **Publishing → Builds** are ready.
Update an existing shared engine after upgrading Core to enable this feature.

Prepared drafts stay in the private R2 bucket. They are not published just because
an import finishes. A publication copies only the required original files and
variants into its public output. Preparation uses image checksums and a versioned
encoding recipe so compatible builds and branches reuse verified variants.
Changing a website or media hostname does not require encoding the same image again.
Republishing does not add a second preparation entry for an unchanged current file.
From Core 0.2.17, automatic upload preparation queues the finalized image by ID;
it does not scan older images just because they lack preparation status. This
applies to browser, API and migration uploads through the same finalization path.
Explicit library preparation and already queued library jobs retain their scope.
Uploads arriving during a running batch are retained for the next batch.
Older media paths and aliases remain available when they are still needed.
Verified cached variants are reused without new encoding or storage writes.

Transfers have per-file progress and bounded concurrency. A failed copy does not
discard successful copies. WordPress imports reuse a persistent source-address
lookup; requests slow down when the source responds with rate-limit or temporary
server errors. Original URLs and existing media aliases are preserved.

A shared build can prepare several batches in one provider run, saving a durable
checkpoint after each batch. It yields before the provider runtime deadline;
another run resumes unfinished work. Image encoding has a separate concurrency
limit from file transfers. The existing website stays live until the new
publication passes verification.

Waiting publications take priority over background image preparation when a
Cloudflare build slot becomes available. An active preparation run finishes its
bounded work first; your Cloudflare account's concurrency limit still applies.

Once preparation is complete, the final build reads the required original and
variant files without repeating storage migration or encoding. After a long
preparation run, it continues in a fresh build with time to finish and upload.

Finished static files are uploaded directly from the trusted customer build
supervisor to Cloudflare Pages with a temporary asset-upload grant. Typeroll
receives a bounded manifest and checksums, finalizes the deployment for the frozen
Site and branch, and checks that the correct publication is reachable on its domain.
Hosting credentials are never passed to the site's renderer.

From Core 0.1.94, the organization’s build engine also verifies new and changed
static files on the deployment candidate. This is a separate job with saved
progress, so an interrupted verification resumes without rebuilding the site.
**Publishing → Builds** shows **Verifying static files** and the checked count.
Previously verified files can be reused when their checksums, hosting account,
project, domains and control files are unchanged. A text edit does not require
re-downloading every unchanged image for verification.

Typeroll performs bounded checks of publication identity and relevant public
responses, including small page, asset and removed-route samples. These checks
are not an exhaustive second download of the site. The existing site remains
available until verification completes. Existing engines must be updated before
starting new shared publications; already frozen older jobs retain their original
artifact and verification path.

Preparation has a six-hour overall limit, and public verification has its own
45-minute window after the build completes. Direct static output is limited to 512 MiB,
20,000 files and 25 MiB per file. Older binary-artifact engines retain their
128 MiB package limit. Images and generated variants remain outside
Git. Corruption, conflicting immutable paths and access errors stop publication;
retry after fixing the reported problem. Verified preparation is retained.

For an existing organization, after upgrading Core, go to **Publishing → Builds**
and select **Update build engine** when no build is running. Wait for verification
before publishing again. Updating the engine does not require reconnecting GitHub
or Cloudflare when the existing connections still have the required permissions.
Independent `npm run build` runs reuse the same verified media; their process
scheduling and time limits belong to your own build environment.

New browser uploads go directly to your R2 account after it is ready. Disconnecting
that account does not silently move uploads back to the hosting operator.

## Verification and retired static bundles

From Core 0.2.16, public verification distinguishes removed content from retired
immutable code bundles. Cloudflare Pages may retain old cached assets for up to
one week. A retired versioned Extension CSS/JavaScript file or hashed Astro
CSS/JavaScript bundle does not block publication merely because its old public
URL still responds. Its absence is still checked on the exact new deployment.
All current files remain verified. Removed Pages, media, and unversioned files
must still disappear; a fresh publication header alone is not proof.

This also applies when the updated server resumes a pending publication. No
account reconnection, manual status override, or site content change is needed.
See [Cloudflare's asset retention behavior](https://developers.cloudflare.com/pages/configuration/serving-pages/#asset-retention).

## Partial builds

From Core 0.2.15, generated publication builds automatically reuse unchanged
pages when a valid previous render cache is available. A normal body-text edit
can rebuild that page while reusing other pages. You still publish a complete
static website; visitors never receive a mixture of deployments.

Listing and reference blocks record the queries they actually use: filters,
selected IDs, ordering, limits and result membership. On the next build these
queries run against the current content, including previously empty results.
Only visited records contribute value dependencies, so a body edit on page 1 of
an archive does not invalidate page 2. Adding, removing, moving, renaming or
changing the status of a Page updates affected lists, references, backlinks,
breadcrumbs and previous/next links without invalidating unrelated Pages.

Unchanged addresses are excluded from Astro's HTML generation queue. Their
verified HTML is restored into the new output directory; removed addresses are
never restored. Shared settings, templates, domains, Core source
and Node versions still invalidate reuse. From Core 0.2.17, custom block templates,
aliases and containers use the same recorded queries and navigation dependencies
as native blocks. Installing a custom block does not make every Page depend on
all other Pages. Changing its definition still invalidates shared output.

Image metadata is tracked by the URLs each rendered page actually uses, including
lookups that currently find no image. Adding or replacing an image rebuilds its
consumers; unrelated pages can reuse HTML. Changing dimensions or variants and
removing an image also invalidate its consumers. Within a query, changes to a
visited record may cause a rebuild even if the changed field is not displayed.
This is dependency tracking, not a promise of minimum possible work.

The route inventory, sitemap, robots rules, redirects, search index and shared
asset processing are regenerated from the complete current site. Removed routes
are never copied from the cache. Image preparation and verified variant reuse
remain a separate process; partial HTML rendering does not eliminate dependency
installation, media transfer, static upload or provider startup time.

Core 0.2.18 (release candidate) adds reuse of unchanged media files already
available in the target Pages project. Updated shared engines compare the
current image completion records with a completed upload receipt, then check
Cloudflare's stored asset hashes before omitting downloads from R2. They combine
reused media and newly generated files into one complete deployment manifest.
Files no longer referenced by the publication are excluded; retained media
aliases remain available when included in the current publication.

Reuse is scoped to the Organization, Site, version, hosting account and Pages
project. Availability is checked again after rendering; missing assets trigger
normal downloads and another render before upload. An expired or invalid receipt
also causes ordinary downloads. The first build with the updated engine creates
the receipt for later builds. Build logs include `media_report` with reused file
and byte counts plus materialization and rendering times. These are separate
from `job.render_report`, which counts HTML routes. Provider startup, dependency
installation and publication verification still take time; the report does not
promise a fixed end-to-end speedup.

For Cloudflare or GitHub shared builds, update the organization build engine in
**Publishing → Builds** after upgrading Core. Both providers use the same renderer
and private R2 cache, isolated per Site and version. Only completed build attempts
can supply a baseline. Cache files expire after seven days; missing, expired or
corrupt files cause a normal full build. Core 0.2.17 introduces media dependency
receipts; its first build refreshes an older cache with a full render. Cache
storage is optional and never a prerequisite for publishing. Older engines continue building in full until updated.

Independent builds of the generated repository retain `.publication-cache.json`
beside `publication.json` between runs. Keep it outside Git and the public `dist/`
directory. The current cache is limited to 32 MiB; a larger cache is discarded.
Use `TYPEROLL_FULL_BUILD=1 npm run build` to compare against a clean full render.
Ordinary starter builds outside the frozen-publication workflow do not use this
cache automatically.

The editor's deployment status reports **pages rebuilt** and **reused** after
rendering. API and MCP clients read `job.render_report` through
`get_deploy_status`; `mode`, `rendered`, `reused`, `total`, `removed` and `reason`
describe actual HTML work. Counts include generated pagination and facet routes.
`get_publication_impact` remains a provisional source comparison, not a prediction
of cache hits or monetary savings.

The generated repository includes public content, renderer source and a dependency
lock. Run `npm ci` and `npm run build` with its pinned Node version to build it on
your own infrastructure. R2 originals remain separate. Cloudflare builds receive
short-lived grants for the exact original and output objects. For independent
builds, provide your own R2 access as described in the generated README.

Forms, Apps and Extensions can still depend on their runtime services; the
repository lists these in `publication.json` under `runtime_dependencies`.
Starting with Core 0.1.81, generated source preserves browser API keys in
Extension configuration fields explicitly declared public by the published
Extension schema. These values are visible in the website and its repository.
Use browser credentials restricted to the intended websites and APIs; keep
server credentials in secret configuration fields. Private keys and GitHub
tokens are rejected even in public configuration. Fields that are private,
secret or absent from the published schema are excluded from the runtime.

A generated site repository is not a full CMS backup.

## API and MCP

Site API keys need admin permission for domain writes. Organization settings
require an organization API key. An external agent can use its own Cloudflare
access to configure DNS and R2 rules, then ask Typeroll to verify them.

| Action                           | MCP tool                               | API route below `/api/v1`                 |
| -------------------------------- | -------------------------------------- | ----------------------------------------- |
| Check setup                      | `read_publishing_readiness`            | `GET /sites/{site}/publishing`            |
| Read site hosts                  | `read_publishing_domains`              | `GET /sites/{site}/publishing/domains`    |
| Save future hosts                | `set_publishing_domains`               | `PUT /sites/{site}/publishing/domains`    |
| Prepare last public snapshot     | `prepare_publishing_domain_change`     | `POST /sites/{site}/publishing/prepare`   |
| Approve verified traffic switch  | `approve_publishing_domain_cutover`    | `POST /sites/{site}/publishing/cutover`   |
| Read organization domain         | `read_organization_publishing_domains` | `GET /publishing/domains`                 |
| Save organization domain         | `set_organization_publishing_domains`  | `PUT /publishing/domains`                 |
| Read media migration             | `read_organization_media_migration`    | `GET /publishing/media-migration`         |
| Retry media migration            | `retry_organization_media_migration`   | `POST /publishing/media-migration`        |
| Read a private image temporarily | `read_private_media_url`               | `GET /sites/{site}/media/{media}/content` |
| Revoke a preview                 | `revoke_preview_link`                  | `POST /sites/{site}/preview-link/revoke`  |

Domain writes include the current `revision`. Cutover also includes `candidate_id`.
A stale revision returns 409. Use the normal deploy-status API to inspect build
progress and `read_publishing_domains` for structured DNS requirements.
