This guide is for operators installing their own CMS. Cloud users can start with
[Using Typeroll Cloud](../typeroll-cloud/); shared editing and publishing guides
are listed in [Cloud and self-hosting](../../getting-started/cloud-and-self-hosting/).

Typeroll CMS is open source (MIT). A self-hosted installation runs in your own
Cloudflare account as two Workers, the portal and Forms, built from the same
release bundle that Typeroll Cloud deploys. Content and accounts live in
Durable Objects and media in R2, both in the EU jurisdiction. There is no
server, container or database to operate.

<Aside type="note">
  Earlier releases documented a Google Cloud profile (Cloud Run, Firebase, Cloud
  Tasks) and a Docker Compose fallback. Both are removed; this Cloudflare
  profile replaces them. Typeroll Cloud adds managed operations, migration
  execution and support on top of the same open-source Core.
</Aside>

## Architecture

```text
Internet ── portal Worker ──┬── Durable Objects (EU): one per site,
                            │   one per organization, one global
                            ├── R2 (EU): media, private drafts, backups
                            └── Cron every 5 minutes (wakes overdue objects)

Internet ── Forms Worker ───── the portal's Durable Objects
```

- **Portal** (`<prefix>-portal`): the editor, public API, hosted MCP and
  sign-in. It owns the `DocumentStore` Durable Object class. Each object's
  alarm delivers its own scheduled work (publishing schedules, Forms
  notifications) through the portal's `Scheduler` entrypoint; a Cron trigger
  every five minutes wakes any object whose alarm is overdue.
- **Forms** (`<prefix>-forms`): the same bundle with `SERVICE_ROLE=forms` on
  its own hostname. It serves only Forms, Analytics and diagnostic routes and
  reaches the portal's objects; it owns no data of its own.
- **Published sites** are static. Each Organization publishes through its own
  build engine and hosting account (GitHub or Cloudflare), as on Typeroll
  Cloud; see [Customer publishing](../customer-publishing/).

## Prerequisites

- A **Cloudflare account** with Workers, Durable Objects and R2. The Workers
  Paid plan is recommended for production.
- Two hostnames for the portal and Forms in a zone of that account, for example
  `cms.example.org` and `forms.example.org`. Without them both Workers answer
  on `workers.dev`.
- A hostname for public media, for example `media.example.org`.
- An email provider for account mail (confirmation and password reset):
  Postmark, Amazon SES or SMTP on a submission port.
- On the machine that deploys: Node.js 22.12 or later, Git and the
  [GitHub CLI](https://cli.github.com) (`gh`), signed in to GitHub, which
  downloads the release and verifies its build provenance.
- **Optional:** each Organization's own Anthropic API key for the built-in AI
  assistant, added in the portal (no server variable).

To try the CMS on your computer first, without any account, follow the
[self-hosting quickstart](../../getting-started/self-hosting-quickstart/).

## Configure

Clone the release you install and its tooling, then copy the two templates:

```bash
git clone --branch core-v<VERSION> --depth 1 https://github.com/typeroll/typeroll
cd typeroll
npm ci
cp config/self-host-cloudflare.example.json self-host.cloudflare.json
cp .env.self-host.example .env.self-host
chmod 600 .env.self-host
```

`self-host.cloudflare.json` holds names and public settings only:

| Setting             | Meaning                                                                                                                               |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `account_id`        | Your Cloudflare account ID                                                                                                            |
| `core_version`      | The Core release to install. Defaults to the version of this checkout                                                                 |
| `bundle_sha256`     | Optional. Pins the exact bundle digest (`sha256:…`); apply refuses any other                                                          |
| `name_prefix`       | Prefix for Worker and default bucket names (default `typeroll`)                                                                       |
| `portal_host`       | Portal hostname, attached as a Worker custom domain                                                                                   |
| `forms_host`        | Forms hostname; must differ from the portal                                                                                           |
| `workers_subdomain` | Only without hostnames: your `<subdomain>.workers.dev`                                                                                |
| `buckets`           | R2 bucket names for `media`, `private_drafts` and `backups` (default `<prefix>-media`, `<prefix>-private-drafts`, `<prefix>-backups`) |
| `media_public_url`  | Public origin of the media bucket, for example `https://media.example.org`                                                            |
| `sites_base_domain` | Optional. Domain for automatic `<slug>.<domain>` site addresses                                                                       |
| `logpush`           | Optional. `true` sends Worker trace events to your Logpush jobs                                                                       |
| `vars`              | Optional public variables, such as your publishing App IDs (see below)                                                                |

`.env.self-host` holds the secrets. Fill in every required value; the file
lists each one with its purpose. Generate each random secret separately:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"
```

Generate the Extension signing key once and store the private JWK as one line:

```bash
node --input-type=module -e "import { generateKeyPairSync } from 'node:crypto'; const { privateKey } = generateKeyPairSync('ec', { namedCurve: 'P-256' }); console.log(JSON.stringify(privateKey.export({ format: 'jwk' })))"
```

`ACCOUNT_EMAIL` is the provider for account mail as JSON, for example
`{"type":"postmark","from":"CMS <cms@example.org>","config":{"server_token":"…"}}`.
SMTP accepts ports 465, 587, 26, 2465, 2525 and 2587; Workers cannot open
port 25.

For media uploads, create an R2 API token with **Object Read & Write** for the
media and private-drafts buckets and put its key pair in `R2_ACCESS_KEY_ID` and
`R2_SECRET_ACCESS_KEY`. The private-drafts bucket keeps uploads that are not
yet published, and SVGs until they are sanitized, out of public reach.

Secrets can also come from the environment instead of the file: pass
`--secrets-env` to the commands below, for example in CI with a secret manager.

Finally, create a Cloudflare API token for deploying, starting from the **Edit
Cloudflare Workers** template. It needs Workers Scripts and Workers R2 Storage
edit access on the account and, for custom hostnames, Workers Routes edit
access on the zone. Export it only in the shell that deploys:

```bash
export CLOUDFLARE_DEPLOY_API_TOKEN=<deploy token>
```

The deploy token is never sent to the Workers. The runtime's own
`CLOUDFLARE_API_TOKEN` in `.env.self-host` is a separate, optional token for
the installation's Cloudflare account. Publishing and Analytics use each
Organization's own Cloudflare connections, not this token.

## Plan

```bash
npm run self-host:cloudflare:plan
```

The plan changes nothing. It:

1. downloads the release bundle (`typeroll-core-<VERSION>-workers.tar.gz` and
   its descriptor) from the Core GitHub release, or uses `--bundle-dir DIR`
   when you have downloaded them yourself;
2. verifies the bundle's digest, file inventory and release contract, and its
   GitHub build provenance from Typeroll's release workflow
   (`gh attestation verify`). A bundle without valid provenance is refused;
3. derives the portal and Forms Worker configurations from the configuration
   the build generated, and builds both without uploading them;
4. reads your account: which buckets exist, whether the Workers exist, their
   Durable Object migration and the names of their secrets.

The output lists the buckets to create, how each Worker will be uploaded, and
which secrets will be set or are missing, by name only. Any problem makes the
command exit non-zero.

## Apply

```bash
npm run self-host:cloudflare:apply -- --confirm <account_id>
```

`--confirm` must repeat your account ID exactly. Apply runs the same checks as
the plan, stops before any change if something is missing, and then:

1. creates the missing R2 buckets in the EU jurisdiction;
2. uploads the portal, then Forms. A first installation, or a release with a
   new Durable Object migration, is deployed in one step (`wrangler deploy`);
   otherwise a new version is uploaded (`wrangler versions upload`) and
   deployed to all traffic (`wrangler versions deploy`). Secrets travel with
   the upload through a temporary file readable only by you, which is removed
   afterwards. Secrets you leave out keep their current value;
3. runs the doctor until both Workers serve the new release and report ready.

What the derived configuration always does:

- binds the store in the EU jurisdiction (`STORE_JURISDICTION=eu`) and every R2
  bucket with `jurisdiction: eu`;
- keeps Workers Logs and traces off and Smart Placement off; with
  `"logpush": true` trace events go to your Logpush jobs instead, for example
  a job to an EU R2 bucket;
- uses no KV namespaces and turns off per-version preview URLs;
- runs the Cron trigger on the portal only;
- records the bundle digest and source commit, so `/api/version` names exactly
  what is running.

A new installation records its data schema in its empty store on the first
request. A store that already holds data but no schema record is never adopted;
the portal then answers 503 until the data is restored or migrated.

Then make the media bucket public on its hostname: in the Cloudflare dashboard
open **R2 → `<prefix>-media` → Settings → Custom Domains** and add the hostname
from `media_public_url`. Do not make the private-drafts or backups buckets
public.

## Verify

```bash
npm run self-host:cloudflare:doctor
```

The doctor checks `/api/version` and `/api/readyz` of both Workers: the
expected release and role, and every required readiness check, which it lists
by name and reason. You can check the same endpoints yourself:

```bash
curl --fail https://cms.example.org/api/version
curl --fail https://cms.example.org/api/readyz
curl --fail https://forms.example.org/api/readyz
```

Then open the portal, create your account, confirm the email address and
create your Organization.

## Upgrade and roll back

Check out the new release tag (or set `core_version`), run `npm ci`, then plan
and apply again. Read the [changelog](https://github.com/typeroll/typeroll/blob/main/CHANGELOG.md)
for the release first: a release that changes the stored data says what to do
before you apply it.

`/api/version` reports the release and the data schema range it can read. A
Worker version is rolled back with Wrangler, for example:

```bash
npx wrangler deployments list --name typeroll-portal
npx wrangler rollback --name typeroll-portal
```

Roll back Forms the same way. A rollback cannot go behind a Durable Object
migration: apply refuses to deploy code older than the store's migration, and
so should you.

## Backups and disaster recovery

A backup is a verified export of the whole document store: every Organization,
Site, Page, setting and account, including password hashes and encrypted
integration secrets. It does not contain media files; they stay in your R2
bucket, which you can copy with any S3-compatible tool.

Backups and restores go through the portal's store transfer endpoint, which is
closed unless `TYPEROLL_STORE_TRANSFER_TOKEN` is set. Add a random value of at
least 32 characters to `.env.self-host` and apply. When you are done, remove it
from the file and delete the secret again:

```bash
npx wrangler secret delete TYPEROLL_STORE_TRANSFER_TOKEN --name typeroll-portal
```

```bash
npm run self-host:cloudflare:backup
```

The backup reads every store object page by page into `backups/backup-<time>/`
(`store.ndjson`, `store.manifest.json` with record counts and SHA-256
checksums, and `backup.json`), checks the files against the manifest, and
copies them to the backups bucket in the EU jurisdiction. `--out DIR` chooses
the directory; `--skip-upload` keeps the copy local. Keep backups as private as
the installation itself.

To restore, for example into a new installation:

```bash
npm run self-host:cloudflare:restore -- --in backups/backup-<time> --confirm cms.example.org
```

`--confirm` must repeat the portal hostname. The restore checks the backup
locally, copies it to the backups bucket, and lets the portal verify, import
and read-compare it in bounded steps. Progress is kept in the bucket, so an
interrupted restore continues when you run the same command again. The import
never overwrites a document whose current value differs from the backup; it
reports it as a conflict and the command exits non-zero. To overwrite such
documents deliberately, run the restore again with `--force` and a new
`--run` name.

Restore into a new installation at least quarterly and sign in to it: a backup
that has only been created is not yet a proven recovery path.

## Accounts and sign-in

People sign up with an email address and password. The portal sends a
confirmation link through `ACCOUNT_EMAIL`; until the address is confirmed the
account sees only **Check your email** and cannot open Organizations, Sites or
API keys. Password reset uses the same provider.

Sessions are kept in the store and last up to 14 days. **Sign out** ends the
session on the server at once.

### GitHub sign-in (optional)

**Continue with GitHub** appears when `GITHUB_SIGNIN_CLIENT_ID` and
`GITHUB_SIGNIN_CLIENT_SECRET` are set. It is separate from the GitHub App that
an Organization connects for publishing and grants no repository access.

1. On GitHub, under **Settings → Developer settings → OAuth Apps**, create an
   OAuth App (not a GitHub App). Use the portal URL as the homepage URL and
   `https://<portal host>/api/auth/callback/github` as the callback URL.
2. Put its client ID and a new client secret in `.env.self-host` and apply.

## Cloudflare sign-in for customer publishing

Customer publishing connects each Organization's Cloudflare account through
your Cloudflare OAuth client. Put its client ID in `vars` as
`TYPEROLL_PUBLISH_CLOUDFLARE_CLIENT_ID` and its secret in `.env.self-host` as
`TYPEROLL_PUBLISH_CLOUDFLARE_CLIENT_SECRET`; the portal also needs its HTTPS
`PORTAL_PUBLIC_URL` (set by the profile) and `INTEGRATIONS_SECRET_KEY`.
Publishing through GitHub likewise uses your own GitHub App:
`TYPEROLL_PUBLISH_GITHUB_APP_ID`, `TYPEROLL_PUBLISH_GITHUB_APP_SLUG` and
`TYPEROLL_PUBLISH_GITHUB_CLIENT_ID` in `vars`, its client secret and private key
in `.env.self-host`.

Cloudflare refuses the whole sign-in (`invalid_scope`) when Typeroll asks for a
scope the client is not allowed, so optional scopes are requested only when you
list them.

| Scope                    | Cloudflare name        | Enables                                                   |
| ------------------------ | ---------------------- | --------------------------------------------------------- |
| `account-settings.write` | Account Settings Write | Create a Site's Web Analytics site when Analytics is on   |
| `account-analytics.read` | Account Analytics Read | Read Web Analytics reports for Insights                   |
| `dynamic-redirect.read`  | Dynamic URL Redirects  | Read Single Redirect rules for redirect hosts such as www |
| `dynamic-redirect.write` | Dynamic URL Redirects  | Create Single Redirect rules for redirect hosts           |

To include them in **Connect Cloudflare**:

1. Allow the scopes on your OAuth client in Cloudflare.
2. List the same scopes, separated by spaces, in `vars` and apply:

   ```json
   "vars": {
     "TYPEROLL_PUBLISH_CLOUDFLARE_OPTIONAL_SCOPES": "account-settings.write account-analytics.read dynamic-redirect.read dynamic-redirect.write"
   }
   ```

Other values are ignored. You may list only some, for example only the two
`dynamic-redirect` scopes. Unset, Analytics access is approved per Site with
**Approve Analytics access**, which requests the two Analytics scopes and still
requires them on the client, and redirect rules are created by hand
(`redirect_rule_required`). Existing connections get the listed scopes when an
owner or admin selects **Approve update** on their Cloudflare card. Approving a
scope enables Analytics for no Site.

## Hosted MCP connector

The portal serves the MCP Streamable HTTP transport at `/api/mcp`. Users add
`https://<portal host>/api/mcp` as a remote server in their MCP client, follow
the consent screen and choose an API key. Issued tokens are signed with
`MCP_OAUTH_SIGNING_KEY` and bound to `PORTAL_PUBLIC_URL`.

Agent clients that run local processes can use the stdio package instead
(`npx -y @typeroll/mcp-server` with `TYPEROLL_API_URL` pointed at your portal):
the same tools and API keys.

## Built-in AI assistant

There is no server-wide AI key. Each Organization adds its own Anthropic API key
in the portal under **Account → AI assistant** and chooses its Sites; see
[Set up the built-in AI assistant](../ai-assistant/). The key is stored
encrypted with `INTEGRATIONS_SECRET_KEY`. The optional `ANTHROPIC_BASE_URL`
variable (in `vars`) points AI calls and key verification at a compatible
endpoint, such as a gateway. MCP and the public API do not depend on any of
this.

## Extensions

A self-hosted portal can register and install private or unlisted Extensions
without contacting Typeroll's hosted catalog. Extension tokens are signed with
`EXTENSION_SIGNING_PRIVATE_JWK`; Native Extension form bindings also use
`FORMS_HMAC_SECRET` and the Forms origin. Customer site deployment remains
static and contains no generated Functions.

The portal publishes issuer discovery and JWKS from its own
`PORTAL_PUBLIC_URL`. Extension providers must pair and validate that issuer
instead of assuming the hosted Typeroll domain. During key rotation, set
`EXTENSION_SIGNING_PREVIOUS_PUBLIC_JWKS` to the old public JWKS for an overlap
window, issue all new tokens with the new private key, then remove the old keys
after the longest token and pairing lifetime has passed.

See [Extensions](../../extensions/overview/) for the manifest, runtime, provider,
and recipient-link contracts.

The Extension protocol does not bundle premium Typeroll Apps. Those apps are
sold and operated separately in Typeroll-controlled accounts even when the CMS
is self-hosted. Third-party and bespoke backends likewise remain in their
developer's accounts. In both cases the browser calls the provider directly;
the self-hosted portal issues identity tokens but never proxies provider API
traffic.

## Settings reference

The profile sets these variables on both Workers from `self-host.cloudflare.json`:
`PORTAL_PUBLIC_URL`, `FORMS_PUBLIC_URL`, `STORE_JURISDICTION=eu`,
`TYPEROLL_STORE_BOOTSTRAP=empty`, `TYPEROLL_SOURCE_SHA` and
`TYPEROLL_BUNDLE_DIGEST`; on the portal also `CLOUDFLARE_ACCOUNT_ID`,
`R2_ACCOUNT_ID`, `R2_BUCKET`, `R2_PRIVATE_BUCKET`, `R2_PUBLIC_BASE_URL` and
`SITES_BASE_DOMAIN`; on Forms `SERVICE_ROLE=forms`. The portal's `MIGRATION`
R2 binding points at the backups bucket.

| Secret                                                                                                                      | Worker        | Required |
| --------------------------------------------------------------------------------------------------------------------------- | ------------- | -------- |
| `AUTH_SECRET` (at least 32 characters)                                                                                      | portal, Forms | yes      |
| `FORMS_HMAC_SECRET`, `INTEGRATIONS_SECRET_KEY`, `EXTENSION_SIGNING_PRIVATE_JWK`                                             | portal, Forms | yes      |
| `ACCOUNT_EMAIL`, `PREVIEW_HMAC_SECRET`, `MCP_OAUTH_SIGNING_KEY`                                                             | portal        | yes      |
| `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`                                                                                  | portal        | yes      |
| `CLOUDFLARE_API_TOKEN`                                                                                                      | portal        | no       |
| `GITHUB_SIGNIN_CLIENT_ID`, `GITHUB_SIGNIN_CLIENT_SECRET`                                                                    | portal        | no       |
| `TYPEROLL_PUBLISH_CLOUDFLARE_CLIENT_SECRET`, `TYPEROLL_PUBLISH_GITHUB_CLIENT_SECRET`, `TYPEROLL_PUBLISH_GITHUB_PRIVATE_KEY` | portal        | no       |
| `EXTENSION_SIGNING_PREVIOUS_PUBLIC_JWKS`, `PAGESPEED_API_KEY`, `SCRAPER_API_KEY`                                            | portal        | no       |
| `TYPEROLL_STORE_TRANSFER_TOKEN` (only while backing up or restoring)                                                        | portal        | no       |
