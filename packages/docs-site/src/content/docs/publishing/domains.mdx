Different settings own different addresses. You can use only the selected
subdomains for Typeroll while keeping the root website, email and unrelated
subdomains on other services.

| Scope         | Setting             | Example                                     |
| ------------- | ------------------- | ------------------------------------------- |
| Organization  | Shared media host   | `media.example.com`                         |
| Hosting Group | Site address base   | `sites.example.com` or `sites2.example.com` |
| Site          | Website host        | `www.customer.example`                      |
| Site          | Redirect hosts      | `customer.example` → `www.customer.example` |
| Site          | Optional media host | `images.customer.example`                   |

A site address base is a parent for generated site and version addresses. It does
not itself serve a website. Default's base is configured in organization setup;
additional groups have their own settings.

## Guided domain move (Core 0.2.107 / MCP 0.45.81)

This guided flow is available in Core 0.2.107 and MCP 0.45.81 or later.
Earlier installations use the existing prepare-and-approve controls below.

Open **Site settings → Publishing → Website and media addresses**. The **Move
site to …** card keeps the hosting account, zone, nameservers, edge certificate,
permissions, publishing prerequisites, redirect capacity and candidate together.
Saving an address is **not** a traffic switch. The card shows the current phase
and only reports **Live and verified** after public checks succeed.

1. Save the future website/media addresses. Changing a prepared output's origins
   requires confirmation before the candidate is replaced. The estimate uses
   recent completed preparations when available; otherwise the duration is unknown.
   Adding/removing redirect hosts retains the content candidate and revokes the
   old traffic approval. Refresh preparation to reconcile redirect requirements.
2. If necessary, expand **Add this domain to the hosting account**. An organization
   owner/admin can create the zone, scan existing DNS, compare discovered records
   with current public answers and copy the reviewed inventory as **DNS only**.
   Existing conflicting records are never overwritten. Scanning is incomplete:
   check the old provider's full inventory, including MX, SPF, every DKIM selector,
   DMARC and verification records. Do not confirm completeness if anything is missing;
   have your DNS administrator or agent supply missing records first.
   This import works only while the zone is pending. Typeroll then gives the exact
   nameservers to enter at your registrar; it never changes the registrar for you.
3. Shortly before changing DNS, select **Prepare for domain switch** to prepare
   the last published snapshot. Later saved CMS edits stay unpublished.
   Compatible cached HTML may be reused for a pure origin change. Changes to the
   renderer, content, indexing policy, derived data or incompatible caches require
   fresh rendering. A cache-format upgrade needs one successful baseline build.
   New preparations freeze the installed renderer while retaining the published
   content. Resuming an existing job keeps its original renderer. Media checkpoints
   and content-addressed files remain reusable independently.
4. Select **Review traffic switch**, review the destination and interruption,
   then approve. For automatic DNS, Typeroll journals the prior records before
   writes and restores them if public verification fails or the agreed window
   expires (15 minutes in the UI; API/MCP allow 5–45 minutes). If another
   administrator changed the records afterward, restoration stops with an explicit
   conflict instead of overwriting their changes. DNS propagation can outlast rollback.
   **Restore previous traffic** uses the same journal. External DNS must be changed
   and restored by its administrator or agent.

The verified build artifact is reused when promoting a candidate to the main
branch; the promotion does not dispatch a second shared build. Temporary media
transfer timeouts use bounded automatic retries of the same frozen job and retain
completed checkpoints. Invalid inputs, denied permissions and integrity failures
are not blindly retried.

From Core 0.2.114, the promoted deployment’s verification uses its new commit
identity, so completion continues the same approved job even though it reused
the earlier build artifact. If an older job stays running after all verification
files are completed, contact support with its job ID; do not repeatedly approve
or create overlapping candidates. After a confirmed rollback, prepare a new
candidate and review its traffic switch again. A rolled-back journal is not reused.

Agents use `guide_publishing_domain_change` (`check`, `preview`, `save`, `prepare`,
`approve`, `rollback`) at `POST /api/v1/sites/{siteId}/publishing/domain-guide`.
`onboard_publishing_domain_zone` uses the organization-scoped
`POST /api/v1/publishing/domain-onboarding` endpoint for zone creation and reviewed
DNS scans. Site-only credentials cannot administer organization zones. The
existing domain tools remain available; replacing a prepared candidate requires
`confirm_rebuild: true` after reviewing the impact. Traffic approval always needs
an explicit human decision about the returned summary.

### Redirect capacity

Cloudflare Pages accepts up to **2,000 static rules**, **100 dynamic rules** and
**1,000 characters per rule**. Wildcards and named placeholders count as dynamic.
Generated trailing-slash variants and hostname aliases count too; the number of
CMS redirect records is not necessarily the emitted rule count. The early source
check conservatively counts every configured rule; final output removes rules
that would shadow actual pages before checking the emitted file. Near the limit,
remove obsolete shadowed rules from the CMS instead of relying on that filter.

Core 0.2.107 replaces Typeroll's old 128 KiB `_redirects` transport limit with
a bounded 10 MiB envelope and checks provider limits in dry-run and upload. Headers
retain their separate 128 KiB bound. There is one `_redirects` file, not several.
A representative 936-rule migration (837 static and 99 dynamic input rules) fits
when its expanded static rules remain below 2,000. A dry-run checks source/export
capacity; only a successful real build verifies the final static artifact.
Do not remove an existing Bulk Redirect list until the replacement publication and
its migration URL checks have passed and its removal is explicitly approved.

## Set organization domains

Open **Account → Publishing → Organization domains**. With Cloudflare DNS access,
choose a domain and enter the short **Media subdomain** and **Sites subdomain**
labels. Review the complete addresses and select **Configure domains**.
The refresh icon next to the domain list retrieves newly available zones.

For external or agent-managed DNS, expand **Manual settings or external DNS**,
supply the full hostnames and follow the returned records. **Check domain status**
reports the current result. Media migration and certificate checks can complete
after settings have been saved; read each status before publishing.

R2's shared media custom domain must belong to a Cloudflare zone in the same
account as its bucket. Keeping authoritative DNS elsewhere requires a supported
Cloudflare partial setup; selecting manual DNS does not remove that provider
requirement. See [external DNS requirements](../../guides/customer-publishing/#when-dns-is-hosted-elsewhere).

## Add a Site's website and media hosts

Open **Site settings → Publishing → Website and media addresses**. Enter the
website host and optional media host. Choose the media path prefix: a separate
media hostname can use an empty prefix, while sharing the website host can use
`/media`.

**Redirect hosts** answer every request with a permanent redirect (301) to the
website host and keep the path and query, for example
`https://www.example.com/about?ref=1` → `https://example.com/about?ref=1`.
Enter them separated by commas.

### Apex domains and www

A website host that is the domain itself, such as `example.com`, is an apex.
Cloudflare Pages serves an apex only when the domain is an **active** Cloudflare
zone in the Cloudflare account of the site's Hosting Group, with Cloudflare's
nameservers at the registrar. A domain whose DNS stays at another provider can use
a subdomain such as `www.example.com` as the website host instead.

A zone that you have just added is **pending**: Cloudflare has not yet seen its
assigned nameservers at the registrar. A pending zone does not proxy records or get
certificates, so neither the apex nor a redirect host in it can serve traffic.
Change the nameservers at the registrar and wait until Cloudflare shows the zone as
active. Records that point at your current host can stay **DNS only** meanwhile.

Typeroll checks the saved hosts against the zones it can read and shows
blockers, such as a pending zone or an apex outside the hosting account, before
you prepare a change.

A redirect host, typically `www.example.com` for an apex website, needs an active
zone in a connected Cloudflare account and must be the zone apex or one level below
it, which Cloudflare's Universal SSL certificate covers. It does not serve pages.
Cloudflare Pages cannot redirect by hostname, and customer sites have no
server-side code, so a **Single Redirect rule** in the zone answers at Cloudflare's
edge. Its record becomes proxied with Cloudflare's placeholder address `192.0.2.1`.
With automatic DNS, Typeroll creates the rule while the host still points at your
current website, where the rule has no effect. Creating it needs the Cloudflare
permission **Dynamic URL Redirects** (OAuth scopes `dynamic-redirect.read` and
`dynamic-redirect.write`; for an API token, **Zone → Single Redirect → Edit**)
on the connection whose account holds the zone. The Zone Transform Rules
permission does not cover redirect rules.

When the installation requests Dynamic URL Redirects during onboarding, a new
connection includes it and the rule is created automatically. A connection made
earlier gets it with one **Approve update** on its Cloudflare card in
**Publishing**. Without the permission, preparation returns
`redirect_rule_required` and the domain panel shows the rule to add under
**Rules → Redirect Rules**; its message also names the permission update when
one is available. An agent can read the `redirect_rules` capability from
`diagnose_organization_cloudflare_connection` before calling
`set_publishing_domains`. A publication is live only after every redirect host
answers 301 to the website host.

For MCP, `set_publishing_domains.redirect_hosts` is an optional array of up to
four hostnames. `approve_publishing_domain_cutover.accept_validation_window` is an
optional boolean; it is not blanket permission to interrupt traffic. Both are
available in Core 0.2.87 / MCP 0.45.67. If a connector rejects them as unknown
before making a request, compare its advertised schema with a fresh `tools/list`
on the same portal endpoint (or `describe_tool` in compact mode). Start a fresh
client conversation after refreshing the connector catalog. Do not bypass schema
validation, change domain settings or reconnect Cloudflare merely to refresh MCP.

A media item's `public_path` can retain an old path such as
`/wp-content/uploads/2024/photo.jpg`; it must end in an extension that matches
the file's type. The next publication uses the selected
active host and paths; saved future hosts take effect only through explicit
domain preparation and cutover. Existing organization media links and previously
published aliases remain usable; changing a preferred host does not invalidate
them. Referenced media is included in static output, not committed as images to GitHub.

## Prepare before switching traffic

**Core 0.2.106 / MCP 0.45.80 (pending release):** saving future domains does not
change normal publication. Keep editing and publishing on the active or temporary
address. Publish your intended content there before preparing the domain switch.

1. Save the future hosts. This records the intended addresses while the current
   public website remains active.
2. Shortly before changing DNS, select **Prepare for domain switch**. The candidate uses
   the last successful publication, not newer saved CMS edits. The build updates
   internal absolute links, canonicals, sitemap URLs and media references.
3. Follow **Domain verification**, applying the returned validation records if
   DNS is managed externally. Wait for the required artifact and certificate checks.
4. When allowed, select **Review traffic switch**, then **Approve and switch traffic**, or apply the reviewed DNS
   change through your provider or AI agent.
5. Wait for Typeroll to verify the actual public address.

Waiting for domain validation or cutover approval does not lock normal
publication. If newer content is published at the current address, the candidate
becomes outdated: prepare again before switching traffic. The candidate contains
the last published content and indexing settings, not unpublished CMS changes.
See [publication destination](../../guides/customer-publishing/#future-hosts-and-the-publication-destination).

Because the candidate rebuilds the last publication exactly, preparation stops
with HTTP 409 and `media_svg_unsanitized` when that publication still contains
an SVG stored before Typeroll sanitized SVG files (Core 0.2.113). Publish the
site once at the current address, which stores and publishes a sanitized copy,
then prepare the domain change again.

When a host already serves another website, Cloudflare Pages validates it only
after its record points at Pages. Typeroll then asks you to accept a short
**validation window**: the host does not answer until Cloudflare finishes, and
Cloudflare does not document how long that takes. Typeroll never changes the
record without that acceptance. See
[switch an apex from an existing host](../../guides/customer-publishing/#switch-an-apex-from-an-existing-host)
and the [full domain-change procedure](../../guides/customer-publishing/#prepare-a-domain-change-before-switching-traffic).

## Use your own AI agent

The API and MCP return the same domain requirements as the UI. An agent with
its own DNS-provider access can apply them, then request verification in
Typeroll. Domain writes use a configuration revision to reject stale changes.
Organization connections require an organization key; site domain writes require
site admin permission. See the [API and MCP mapping](../../guides/customer-publishing/#api-and-mcp).

For sites still using the older managed publishing mode, use the separately
labelled [legacy managed-domain guide](../../guides/custom-domain/).

## Different generators under one hostname

Domain settings select a website host, not which repository serves each path.
For a CMS site with independently generated docs at `/docs/`, follow
[Different generators on one website](../multiple-generators/). That separate
hosting configuration must also be preserved during domain changes.
