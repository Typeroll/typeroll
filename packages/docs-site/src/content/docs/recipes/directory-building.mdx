---
title: Build and import a structured directory
description: Field types, editable landing pages, ownership, SEO and resumable imports for agent-built directories in Typeroll CMS.
---

This recipe applies to Typeroll Cloud and self-hosted Typeroll CMS. The
`multiselect` field, mapped-only schema, shared sitemap route inventory and
`read_app_documentation` require Core **0.2.8** and MCP **0.45.8** or later.
Check the connected server's version before relying on them. A locally upgraded
MCP client does not upgrade the site's server.

## Discover before writing

Call `read_app_documentation` on the selected site. It returns the public guides
and instructions for enabled core modules, plus documentation supplied by each
enabled Extension's resolved release. Missing provider documentation is reported
explicitly. These are reference materials, not permission to publish or send
messages. Then read content types, templates, Pages and block schemas. Use the
same `version` for every versioned call during an import. App activation is
site-wide; content, templates and publication are versioned.

All records are Pages. Content types define fields and routes; templates define
presentation and may be shared or overridden per Page. A directory does not
need a second record API or a special editor.

## Field contract

`create_content_type` and `update_content_type` accept these custom field types:

```text
text textarea richtext image file color select multiselect boolean number
url email date datetime list list_simple array object page_ref page_ref_list
```

Every definition needs `name`, `label` and `type`. Names use lowercase letters,
numbers and underscores, starting with a letter. Title, slug, status, block body,
SEO and `noindex` are built-in Page fields, not custom fields. `email` and `url`
were already supported before 0.2.8; a rejected request needs its exact error and
payload checked. Their Page validation checks string shape; validate source
email/URL syntax in your importer as well.

Example `fields` for a supplier type:

```json
[
  {
    "name": "claim_email",
    "label": "Claim email",
    "type": "email",
    "rendered": false,
    "writable_by": ["portal", "agent", "import"]
  },
  {
    "name": "website",
    "label": "Website",
    "type": "url",
    "writable_by": ["portal", "owner", "agent", "import"]
  },
  {
    "name": "service_scope",
    "label": "Service scope",
    "type": "select",
    "options": ["national", "states", "unknown"],
    "writable_by": ["portal", "owner", "agent", "import"]
  },
  {
    "name": "service_states",
    "label": "States served",
    "type": "page_ref_list",
    "ref_content_type": "states",
    "writable_by": ["portal", "owner", "agent", "import"]
  },
  {
    "name": "product_categories",
    "label": "Product categories",
    "type": "page_ref_list",
    "ref_content_type": "product-categories",
    "writable_by": ["portal", "owner", "agent", "import"]
  },
  {
    "name": "group_types_served",
    "label": "Group types served",
    "type": "page_ref_list",
    "ref_content_type": "group-types",
    "writable_by": ["portal", "owner", "agent", "import"]
  },
  {
    "name": "mechanics",
    "label": "Mechanics",
    "type": "multiselect",
    "options": ["preorder", "online_store", "direct_sale"],
    "writable_by": ["portal", "owner", "agent", "import"]
  },
  {
    "name": "seasons",
    "label": "Seasons",
    "type": "multiselect",
    "options": ["spring", "summer", "fall", "winter", "year_round"],
    "writable_by": ["portal", "owner", "agent", "import"]
  },
  {
    "name": "source_ids",
    "label": "Source ID",
    "type": "text",
    "rendered": false,
    "writable_by": ["portal", "agent", "import"]
  }
]
```

Adapt controlled choices to the source's validated vocabulary before importing.
A `multiselect` value is an array of unique allowed strings; options are required.
An empty array clears it, and null represents an unknown optional value. Existing
text is **not** automatically split or converted. Read values, map deliberately,
then validate and save. Arrays filter by membership. For Directory owner forms,
a `multiselect` form field produces a checkbox group; field names must match the
content schema. A cleared checkbox group clears the selection.

Use text for city, state abbreviation, rating and sourced profit-share wording;
number for founded/verified year; textarea for policies and shipping notes;
boolean for verified yes/no facts. Unknown is null/absent, never an invented
false. A custom `claim_status` does not automatically track Directory edit grants.

`rendered: false` removes custom fields recursively from public Page output. It is
not a per-user read permission. Do not copy hidden values into blocks or JSON-LD.
`writable_by: ["owner"]` excludes agent and portal editors. List each intended
writer explicitly. Owner changes outrank later agent/import changes; report HTTP
409 conflicts instead of retrying to overwrite them. Bearer API calls are agent
writes, even if the schema also allows `import`.

## Editable landing pages and listings

These routes need no special routing feature:

| Content type       | Route template        |
| ------------------ | --------------------- |
| suppliers          | `/companies/{slug}`   |
| product-categories | `/fundraisers/{slug}` |
| group-types        | `/ideas/{slug}`       |
| states             | `/states/{slug}`      |
| articles           | `/guides/{slug}`      |

Create a Page for each category, group or state so it can hold unique editorial
content, its own SEO and an intentional `noindex` decision. Resolve references to
Page IDs, not slugs. National suppliers can use `service_scope: national`; do not
invent fifty regional relationships. Show national suppliers separately from
region-specific results when that distinction matters.

A `core/page_list` uses `content_type: "suppliers"`, `filter_field:
"service_states"` and `filter_value` equal to the state Page ID. For backlinks,
use `core/repeater` with `source_type: "backlinks"` and `content_type:
"suppliers"`; the current Page identity supplies the match. Backlinks include
all reference fields from that type. Use `core/page_list` with `filter_field`
when a specific relationship must be selected. Read the actual block schema
before selecting its `item_block` and card presentation. Use `source_type:
"related"` and `field` on a supplier to follow one of its reference fields.
Configure `empty_state` for sparse records. Changes reach these static listings at the next publication.

Set parent Page relationships when the URL hierarchy represents a real parent.
That supports breadcrumbs; a many-to-many reference is not automatically a
breadcrumb parent. Set distinct, factual `seo_title` and `seo_description` on
Pages; templates do not invent unique SEO text from missing data. Render one
visible H1 and semantic headings, tables with header cells, and real anchor links.

## Facets and indexing

Prefer editable landing Pages for a curated category × state subset. Automatic
facets are suitable for simple scalar vocabularies, not raw Page reference IDs:
reference values currently slugify the IDs, without resolving titles.

`facet_combinations: [["category", "state"]]` means a pair of **configured facet
field names**. It generates every qualifying value combination for that pair.
It is not a list of specific category/state values. `min_items` counts records;
it does not measure regional differentiation or prevent doorway pages. Leave
combinations unset until their outputs are worth publishing. Do not configure
facets on the same paths as your editorial landing Pages. Stored Page paths win
collisions; generated paths use one deterministic inventory for rendering and
sitemap.

A custom `fields.indexable` has no SEO meaning. Use:

```json
{ "page_id": "the-state-page-id", "patch": { "noindex": true }, "save": true }
```

with `update_page`. Set site language explicitly to `en` and trailing slash to
`always` through site settings; inspect Page language/canonical overrides. Do not
reuse another site's settings. Keep pre-launch protections until an authorized
launch. At launch, review sitewide noindex, version `robots_blocked`, and the
explicit `robots_txt` crawl block separately. Blocking crawling is not equivalent
to noindex. Preview/version/fallback-host protections are separate from the
production domain.

Run `check_site_indexing`, then inspect actual HTML robots, response headers,
canonicals, robots.txt and sitemap. Compare sitemap URLs with all published,
routed, non-noindex Pages **across all content types**, plus generated facets and
pagination. Unlisted Pages are not sitemap entries. A green root diagnostic does
not establish complete route coverage. Query filters should link to intentional
static URLs; query combinations do not automatically become SEO pages.

## Structured data

Use `schema_type: "Organization"` on a supplier content type, with
`schema_field_mode: "mapped"` and `schema_field_map:
{"title":"name","website":"sameAs"}`. Mapping direction is **field → Schema.org
property**. Mapped mode includes only named fields, retaining the canonical `url`
and type/context. It does not add publisher or date fallbacks. Hidden fields stay
excluded. Default `all` mode retains the older automatic mapping behavior and may
include public custom data under its original names; choose deliberately.

For nested addresses, service areas or typed references, resolve the referenced
Pages yourself and write a reviewed `Page.json_ld` graph. Disable the content
type's automatic schema by setting `schema_type: ""` when replacing it with a
manual graph. Also inspect Page `schema_type`, `kind` and the site's automatic
Organization/Article output to avoid contradictory entities. Do not pass internal
Page IDs as `areaServed` or rely on dotted mapping names to build nested objects.
A controlled graph can contain `{"@type":"State","name":"California"}` or a
public referenced URL. Keep it synchronized when referenced facts change.

Describe sourced facts in visible semantic content. Product/Offer is for actual
products/offers; fundraising profit share is not a product price. FAQ/Article
markup must match the content. JSON-LD is the normal metadata path; add microdata
only deliberately, without duplicating conflicting claims. Neither schema nor
static routes guarantee rankings, rich results or AI citations.

## Resumable census imports

1. Call `get_import_readiness` before importing; customer storage must be ready.
2. Validate source JSON locally: unique stable namespaced IDs, controlled choices,
   real state codes, URL/email syntax, and null versus known boolean values.
3. Pick one version. Paginate `list_pages` (limit at most 200) for relevant types;
   build source-ID and taxonomy maps. Refuse ambiguous duplicate source IDs.
4. Create missing taxonomy Pages first. Persist returned IDs immediately. Resolve
   state codes/slugs to Page IDs and quarantine unresolved references. The field
   schema itself does not guarantee that every referenced Page exists.
5. Create a Page only for an unknown source ID. Otherwise read it, compare the
   import-owned fields and call `update_page` with `patch.fields` and `save: true`
   only when values differ. Preserve block bodies, SEO, other fields and owner
   corrections. Resolve any working copy deliberately before updating saved data.
6. Persist checkpoints. If a create response is lost, relist and reconcile its
   stable source ID before retrying. Serialize imports for a site/version: this
   workflow is **not an atomic unique-source upsert API**. Do not run competing
   importers and assume uniqueness is enforced.
7. Repeat the same import: expect no duplicates and no writes for unchanged data.
   Test full/sparse/national/regional records, references, backlinks, empty states
   and private-field exclusion in actual HTML and JSON-LD.
8. Use `get_preview_link`; a bare preview path is not an authenticated preview.
   Save and deploy only with authorization, then validate the static output.

Keep claim email, production DNS and launch separate from data modeling. The
Directory module can be configured before outbound messages are authorized.
