Pages, partials, Page templates all share one editing surface: a tree of **blocks**. The AI agent reaches for blocks instead of writing raw HTML — it's faster, more consistent, and the same edits the AI agent makes are what you see in the editor's drag-and-drop panel.

## The two verb families

There are two distinct kinds of block tools — keep them straight:

- **Block-instance tools** — `add_block`, `update_block`, `move_block`, `remove_block`, `duplicate_block`, `set_block_responsive`, `get_page_blocks`. These place + edit _instances_ of blocks inside a container.
- **BlockType tools** — `list_block_types`, `read_block_type`, `create_block_type`, `update_block_type`, `delete_block_type`, `find_pages_using_block_type`, `export_block_types`, `import_block_types`. These manage the _type definitions_ — the things that show up in the block picker.

> Asking "add another testimonial to the home page" is instance work. Asking "make me a custom price-card block with a built-in star rating" is type work.

## Block containers

A container is anything that holds a tree of blocks. Four kinds:

| Kind       | What it is                                | `target.id`                                |
| ---------- | ----------------------------------------- | ------------------------------------------ |
| `page`     | A regular page in blocks-mode             | The page's id                              |
| `partial`  | A header/footer/free block in blocks-mode | `"header"`, `"footer"`, or a free-block id |
| `template` | A page template                           | The template id (e.g. `"blog-post"`)       |

Every instance tool accepts the same shape:

```
target: { kind: "page" | "partial" | "template", id: string }
```

For pages, `page_id: "<id>"` is a shorthand for `target: { kind: "page", id: "<id>" }`. Older prompts still work; new patterns should prefer `target`.

```
"Add a feature_grid in the header that appears on every page."
  → add_block target={kind:"partial", id:"header"} block={type:"core/feature_grid", ...}

"Build a blog post template — featured image at the top, then title, then the post body."
  → add_block target={kind:"template", id:"blog-post"} block={type:"template/page_featured_image"}
  → add_block target={kind:"template", id:"blog-post"} block={type:"template/page_title"}
  → add_block target={kind:"template", id:"blog-post"} block={type:"template_content_slot"}

"Change how every blog post lays out — show the date next to the title, then a wide image."
  → add_block target={kind:"template", id:"article-layout"} block={type:"template/page_title"}
  → add_block target={kind:"template", id:"article-layout"} block={type:"template/page_date"}
  → add_block target={kind:"template", id:"article-layout"} block={type:"template/page_featured_image"}
```

## The block library

The AI agent calls `list_block_types` first to see what's available on the current site (core + custom + third-party in one list). Don't memorise ids — they're per-site. The library covers ~40 blocks across these groups:

### Layout primitives

- `core/section` — outer container with width + padding + bg
- `core/container` — flex container (direction / wrap / gap / align)
- `core/grid` — N-column grid that wraps automatically
- `core/columns` — 2-slot Left/Right container for asymmetric layouts
- `core/spacer`, `core/divider`

### Content + marketing

- `core/heading`, `core/prose`, `core/button`, `core/image`, `core/icon`, `core/icon_box`
- `core/hero` (4 layout variants), `core/cta`, `core/feature_row` (gutter-hugging image + text row)
- `core/accordion`, `core/tabs`, `core/video`, `core/form`, `core/media_card`
- `core/search` — see [Site search](#site-search) below
- `core/html` — the raw-HTML escape hatch for one-offs no block covers. Output is sanitised the same way HTML-mode pages are, so it isn't a script vector.

### Article content and automatic contents

Use `core/table`, `core/list`, `core/image`, `core/video` and formatted headings
for editable article content. Tables support header cells, spans, colors,
column widths and horizontal scrolling. Images support original dimensions,
alignment, a separate mobile image, a link and formatted photo credits.

Place **`core/table_of_contents` in the Page template**, next to its
`template_content_slot`. It derives links from the current Page's headings;
there is no editable list or source content field. Choose `h2`, `h2-h3` or
`h2-h4`. Changing, moving or removing a heading updates the generated list.
Existing heading anchors are preserved and links are present without JavaScript.
You can choose a plain list or card, indentation, desktop stickiness and
highlighting of the current heading. On mobile it stays in normal document flow.
The same block also works inside a Page body.

The Article template starter places its table of contents beside the body on
larger screens and before the body on mobile. The Two columns block's **Mobile
order** setting controls this order independently of the desktop layout.

### One main heading and mobile defaults

From **Core 0.2.13**, a Page template that provides an H1 (usually **Page title**)
owns the Page's main heading. Use H2 for headings in the Page body. The editor's
Save action and API writes reject a body H1 that duplicates the template title,
with an explanation of how to fix it. A Page without a template H1 can keep its
own body H1. HTML-mode Pages also allow only one H1.

Existing content remains editable: preview and static builds render additional
body H1 headings as H2, preserving their text and anchors. A known template H1
always takes precedence. The layout does not add another automatic Page title.
This safeguard does not rewrite saved content; correct the heading level before
saving a changed body. Custom header/footer HTML should use a non-heading element
for the site brand.

Repeater grids, including **Page list**, show one column below **768 px** by
default. Set **Mobile columns** (`mobile_cols`, 1–6) only when multiple columns are
intentional. An explicitly authored `cols.mobile` is also respected;
`mobile_cols` takes precedence. At 768 px and wider, the normal `cols` settings
apply. This listing-specific threshold does not change the general responsive
breakpoints used by other blocks. Masonry remains an explicit layout choice.

The default content gutter is **1.25 rem** below 768 px and **1.75 rem** above it.
Full-width section backgrounds still reach the viewport edges, while their
content has the same gutter. Site CSS can customize `--content-gutter`.
These shared defaults apply to both Cloud and self-hosted sites after upgrading
Core and rebuilding the site; previously published files remain unchanged.

### Structured Page fields without empty labels

**Requires Core 0.2.12 and template capability `supports_page_field_list`.**
Cloud and self-hosting use the same block; check the deployed site's capabilities
before adding it.

Add **Page field list** (`core/field_list`) to a Page template to present typed
values from the current Page's `fields`. Rows use a 0.7 rem vertical gap, labels use
font weight 600, and long values wrap to avoid horizontal overflow (Core 0.2.13). Choose the content type's field names;
leave each label blank to use its schema label. Values stay in the structured
field editor. Changing and saving a Page field updates preview and the next
publication without editing the Page body or copying values into rich text.

```json
{
  "id": "facts",
  "type": "core/field_list",
  "data": {
    "title": "At a glance",
    "layout": "two-column",
    "fields": [
      { "field": "website" },
      { "field": "headquarters", "label": "Based in" },
      { "field": "shipping" },
      { "field": "regions" }
    ]
  }
}
```

The example assumes those fields are declared on the Page's content type.
The block renders a semantic definition list. `stack` is the default layout;
`two-column` becomes a single column on small screens. The optional heading is
an H2. Use multiple field-list blocks for independently titled sections.

- Null, missing values, blank strings (including whitespace), and empty lists
  omit the **whole row**, including its label.
- If no rows remain, the **whole block and its heading** are omitted from HTML.
- Number `0` is a value. From Core 0.2.14, boolean rows default to
  `boolean_display: "property"`: show **Yes** for true and hide false/unset.
  Choose `boolean_display: "yes-no"` to show both set values. `true_label` and
  `false_label` let you use labels such as **Ja** / **Nej**. This changes
  presentation only; false remains a stored value. Core 0.2.12–0.2.13 displayed
  both set booleans as True/False.
- Text and textarea values are escaped. URLs become HTTP(S) or site-relative
  links; unsafe URLs are omitted.
- Select and multiselect fields use `option_labels` when configured, falling
  back to the stored option. Multiselect values render as a list.
- `page_ref` and `page_ref_list` resolve to Page titles and links. Missing,
  unpublished, unlisted or unrouted targets are omitted. Lists preserve the
  selected order without duplicate links.
- Unknown fields, unsupported field types, and fields with **`rendered: false`**
  never render. A private field cannot be exposed by selecting or styling it.

#### Fine-tune an individual row

Each row optionally accepts `html`, `css` and `css_class`. For example:

```json
{
  "field": "shipping",
  "html": "<dt>{{label}}</dt><dd><span class=\"badge\">{{value}}</span></dd>",
  "css": "padding: 0.75rem; background: #f3f6fa; border-radius: 0.5rem;",
  "css_class": "shipping-fact"
}
```

`html` replaces the contents of that row's wrapper. Keep a `dt` label and `dd`
value for definition-list semantics. Its only slots are `{{label}}` (escaped
label) and `{{value}}` (the safely formatted value, including links or lists).
Place the value slot in element content. No Page expressions or conditionals are
evaluated, and values are never reinterpreted as template code. Custom markup
passes through the normal HTML sanitizer; it cannot add scripts or event handlers.

`css` contains CSS declarations applied to that row's wrapper. For more detailed
selectors, give the row a `css_class` and use the block's existing **Custom CSS**
setting, for example `.shipping-fact .badge { font-weight: 600; }`.
Empty and private fields are omitted **before** custom row markup or styles are
applied; a custom label or placeholder cannot make an empty row visible.

#### Checkbox lists with icons and selected links

A multiselect already renders one selected option per list item. Set
`item_html` on that field's row to customize each selected option. For example:

```json
{
  "field": "delivery_methods",
  "css_class": "delivery-options",
  "item_html": "<span class=\"checked-box\" aria-hidden=\"true\">☑</span> <span>{{value}}</span>",
  "item_links": [{ "value": "local_pickup", "url": "/delivery/local-pickup/" }]
}
```

If `local_pickup` has the schema label **Local pickup**, the visitor sees that
label as a link; other selected options remain plain labels. `item_links`
uses stored option values for matching. Unsafe link URLs are ignored. You can
use a custom image inside `item_html` instead of the checkbox character.

Use the block's Custom CSS for the list and icon, for example:

```css
.delivery-options .field-list-values {
  list-style: none;
  padding: 0;
}
.delivery-options li {
  display: flex;
  align-items: baseline;
  gap: 0.5rem;
}
.delivery-options .checked-box {
  color: #087044;
}
```

Within `item_html`, `{{value}}` is the formatted option label (including its
configured link) and `{{label}}` is the plain escaped option label. The same
item template can decorate Page references; their links still come from the
referenced Pages rather than `item_links`. Unselected options never render;
clearing the field removes the entire row, including its heading and icons.
This is presentation stored once in the Page template, not copied Page content.

Agents use the existing `list_block_types`, `read_block_type` and `add_block`
tools with `target: { "kind": "template", "id": "profile" }`. Inspect the content
type first. Do not generate per-Page facts HTML or a duplicate rich-text field.

### Typography in a Page template

In Core 0.2.2 and later, select the template's **Page content** block to set
**Body text size (px)**, **Body line height**, and **Paragraph spacing (em)**.
For example, 16 px with a line height of 1.6 produces 25.6 px lines. Leave a
field empty to keep the block defaults. The settings apply inside that content
slot; navigation, related cards and other template content keep their own styles.
They do not change the saved text or require custom CSS.

### Related Pages

For a curated list, use `core/repeater` with **Source: Pages** and select Pages
in the desired order. Leave Content type empty to combine articles, checklists
and other types. **Exclude current Page** removes the page being displayed.
Missing and unpublished pages are omitted before the item limit is applied.

In a shared Page template, use **Source: Related** and name a Page reference
field from the Content type. Each Page then supplies its own selection, while
the template owns the card layout. Use **Backlinks** to list pages referring to
the current Page. `core/post_card` provides the image, title and link presentation.

### Item-compatible kernels

Designed to tile cleanly inside a repeater — no outer padding, kernel layout. Render fine standalone too.

- `core/testimonial`, `core/team_member`, `core/pricing_plan`, `core/post_card`, `core/logo_item`, `core/step_card`

### Repeater + aliases

The repeater abstraction collapses what used to be a dozen specialised widgets into one primitive. The aliases are author-friendly wrappers:

- `core/gallery` — image grid
- `core/logo_cloud` — client logos (greyscale by default)
- `core/testimonials` — testimonial carousel
- `core/feature_grid` — icon_box grid
- `core/pricing_table` — pricing_plan grid
- `core/team_grid` — team_member grid
- `core/page_list` — Pages of any content type, items become post_cards

Each alias accepts `items: [{...}]` directly — the AI agent passes the per-item field values and the renderer expands the alias to a repeater with the right item-block type.

```
"Add a feature grid with our three differentiators."
  → add_block block={type:"core/feature_grid", data:{items:[
       {icon:"zap", heading:"Fast", text:"<p>...</p>"},
       {icon:"shield", heading:"Safe", text:"<p>...</p>"},
       {icon:"smile", heading:"Simple", text:"<p>...</p>"}
     ]}}
```

### Template/\* family (dynamic context)

These read from the render context (`page`/`site`/`item`) rather than from authored block data. Used inside Page templates so a blog template can render every post with its own title without per-post copy.

- Page-context: `template/page_title`, `template/page_featured_image`, `template/page_excerpt`, `template/page_date`, `template/page_author`, `template/page_breadcrumbs`
- Site-context: `template/site_logo`, `template/site_title`, `template/site_tagline`
- Item-context: `template/page_title`, `template_content_slot`, `template/page_featured_image`
- Conditional: `template/show_if` (renders children only if a condition is truthy)

## Site search

Add `core/search` to a page and your published site gets working full-text
search. There is nothing to configure and no third-party service involved:

```
Add a search box to the header.
```

At deploy time, if any page uses the block, the built HTML is indexed with
[Pagefind](https://pagefind.app/) and the index ships as static files alongside
the site. Search runs entirely in the visitor's browser against that index — no
search server, no per-query cost, and it works on any static host.

Sites without the block skip the indexing step entirely, so adding search costs
build time only when you actually use it.

The only field is `placeholder`. The result UI inherits your site's colours
through the same CSS variables as everything else.

## Responsive — 5 breakpoints, fluid type

Headings and prose already shrink fluidly on small screens — no per-page tuning needed. Beyond that, any field marked `responsive` accepts a per-breakpoint object.
Put that object on the field inside `block.data` (`data.cols`, for example).
The unrelated historical top-level shape `block.responsive` is not rendered
and is rejected by whole-tree writes as well as block-instance tools.

The five breakpoints are Tailwind-compatible:

| Token     | Min width | Use                           |
| --------- | --------- | ----------------------------- |
| `mobile`  | 0         | Baseline                      |
| `tablet`  | 640px     | Stora telefoner, små tablets  |
| `laptop`  | 1024px    | Tablet landscape, små laptops |
| `desktop` | 1280px    | Vanlig desktop                |
| `wide`    | 1536px    | Stora skärmar                 |

Mobile-first inheritance: missing breakpoints inherit upward from the previous defined one.

```
"Make the feature grid 1 column on mobile, 2 on tablet, 3 on desktop."
  → set_block_responsive block_id=<feature_grid_id> field=cols
       value={mobile:1, tablet:2, desktop:3}
```

`Block.hidden_on: ['mobile']` hides the entire block at a breakpoint — no BlockType opt-in needed.

## Authoring custom block types

When the library doesn't fit, the AI agent creates a custom type with `create_block_type`. The block ships immediately to the editor + the renderer's registry — no deploy needed.

```
"Make a 'quote with avatar' block: square photo on the left, quote + name on the right."
  → create_block_type
       name="quote_with_avatar"
       label="Quote with avatar"
       schema=[{name:"photo", type:"image", label:"Photo"},
               {name:"quote", type:"richtext", label:"Quote"},
               {name:"name", type:"text", label:"Name"}]
       template="<figure data-block='quote_with_avatar'>
                   <img src='{{photo}}' alt='{{name}}' />
                   <blockquote>{{{quote}}}</blockquote>
                   <figcaption>— {{name}}</figcaption>
                 </figure>"
       styles="[data-block='quote_with_avatar']{display:flex;gap:1rem}
               [data-block='quote_with_avatar'] img{width:6rem;border-radius:50%}"
```

<Aside type="caution">
  **Custom JavaScript is not available through the AI agent.** Block-level JS
  runs in every visitor's browser with full DOM access — that's a trust decision
  a human takes. To add a script to a custom block, open it in the portal's
  block-type editor, toggle "Activate JS", and accept the warning.
</Aside>

Origin is auto-stamped `'ai'` so the portal UI can visually flag AI-authored blocks for audit.

## Editing existing types

`update_block_type` patches fields on an existing custom or third-party block type. Core blocks (id starts with `core/`) are managed in platform code and can't be changed via tool. Schema, template, and styles **replace wholesale** when included — don't send them unless you want to overwrite. The script field is silently dropped even on updates.

```
"Make the testimonial block default to bordered style instead of card."
  → update_block_type id="<custom-testimonial-id>" schema=[…updated schema…]
```

`delete_block_type` removes a custom type. Pages currently using it render `<!-- unknown block type -->` comments instead, so the AI agent calls `find_pages_using_block_type` first and asks before deleting when there's usage.

## Reorganising blocks

- `move_block` — re-parent or reorder inside the same container. Cycles rejected.
- `duplicate_block` — clones a block (subtree included), inserts the copy right after the original, returns the new id. Easiest way to add another card to a feature grid.
- `remove_block` — drops a block and everything inside it.

## Responsive defaults and CSS order (Core 0.2.14)

These defaults are shared by Typeroll Cloud, self-hosted preview, and newly
published static builds. Existing published sites change only after rebuilding.
Explicit block settings and site CSS remain in place; remove temporary corrective
CSS only after comparing preview with the intended design.

| Default                    | Phone               | Tablet (768px)      | Desktop (1280px)    |
| -------------------------- | ------------------- | ------------------- | ------------------- |
| H1 / H2 / H3 / H4          | 28 / 22 / 18 / 16px | 32 / 24 / 20 / 17px | 36 / 24 / 20 / 18px |
| Section vertical padding   | 48px                | 64px                | 80px                |
| Gap between section blocks | 24px                | 24px                | 32px                |
| Card inset / grid gap      | 16px                | 24px                | 24px                |
| Content gutter             | 20px                | 28px                | 28px                |

H5 and H6 use 16px and 14px at every width.

Values assume a 16px base font. Semantic headings use line heights 1.2 / 1.25 /
1.3 / 1.35; body uses 1.55. Explicit heading sizes such as `article` retain their
own scale. Section `padding_y: "auto"` and grid/repeater `gap: "auto"` select the
responsive defaults; fixed named sizes remain deliberate overrides.

Use `core/section` or `core/hero` as the top-level background carrier. Its
background reaches the viewport edge; its inner content has gutters and a maximum
width. Do not wrap these blocks in a padded main container. Adjacent sections
receive no extra outer gap on top of their vertical padding. Nesting a section
inside a constrained column deliberately constrains that section too.

Images use intrinsic height and `contain` by default. `core/image` and
`template/page_featured_image` accept `fit` and `aspect_ratio`; `core/post_card`
accepts `image_fit` and `image_aspect`, and `core/media_card` accepts `image_fit`.
Choose a ratio plus `cover` only when cropping is intended. Hero `full-image` is
an explicit background-cover layout; other hero layouts preserve the complete
image. Test at 375, 768 and 1280px with the actual artwork.

Navigation uses the same CSS and JavaScript boundary: through **1023px** it is a
collapsible menu; from **1024px** links appear inline. Without JavaScript, links
remain reachable. Escape closes the mobile menu and returns focus to its button.

`core/list.marker` supports `auto`, `none` and `check`. Use `none` for a custom
icon already in each row, or `check` for one native checkmark. Native checkbox
inputs suppress the extra marker. Field-list `item_html` owns item decoration:
Typeroll removes native bullets so a custom checkbox icon is not doubled.

Breadcrumbs have 0.75rem before and 2rem after; from 1024px they use 1rem and
2.5rem. They do not add an additional section-block gap below the trail.
Override `--breadcrumbs-before` and `--breadcrumbs-after` without changing links
or structured data.

### Theme tokens and precedence

The shared scale is `--space-1` through `--space-12` (4, 8, 12, 16, 24, 32,
40, 48, 64, 80, 96, 128px at a 16px root). Override semantic tokens instead of
patching individual blocks: `--section-padding`, `--block-gap`,
`--block-gap-tight`, `--block-gap-loose`, `--grid-gap`, `--card-padding`,
`--content-gutter`, `--type-h1` … `--type-h6`, `--type-lead`, and
`--body-leading`. Theme fonts and colors remain independent.

```css
:root {
  --type-h2: 1.5rem;
  --content-gutter: 1rem;
}
@media (min-width: 768px) {
  :root {
    --content-gutter: 1.5rem;
  }
}
@media (min-width: 1280px) {
  :root {
    --content-gutter: 2rem;
  }
}
```

Preview and static output load CSS in the same order: platform defaults and theme
variables → block definitions and generated instance/responsive styles → site
Custom CSS → Page Custom CSS. This is source order, not a replacement for the CSS
cascade: specificity, inline declarations and `!important` still take precedence.
Use block settings first, theme tokens for shared decisions, and scoped custom
CSS for deliberate exceptions. Preview does not yet diagnose cascade conflicts.

### Saved blocks and publishing readiness

Whole-tree writes assign missing, invalid or duplicate block IDs recursively,
including children and slots. Malformed trees are rejected with a field path;
they are never silently accepted or turned into empty content. IDs are assigned
before storage, including editor working copies, API batch writes and MCP calls.

`read_publishing_readiness` also validates the saved, version-resolved content:
invalid IDs, unsupported block types and missing referenced Page templates block
publication with `content_export_invalid` and an editable resource path. Draft
Pages and unsaved editor changes do not enter the public export. The same
validation runs when freezing source and exporting content. It reads content and
validates the export contract; it does not build the site or process images.
Readiness is a preflight, not a guarantee that a later provider operation will
succeed. Accepted jobs continue from their frozen source, not later edits.

### Precise native presentation

The **Core 0.2.25 candidate** adds optional dimensions without requiring custom CSS.
Use `read_block_type` to confirm that the connected runtime exposes these fields;
Cloud and self-hosted installations gain them when upgraded. Existing size presets
remain the default. Numeric dimensions accept a number or a responsive object,
for example `font_size_px: { mobile: 30, laptop: 48 }`. Breakpoints are mobile 0,
tablet 640, laptop 1024, desktop 1280 and wide 1536 pixels. Values inherit from the
previous breakpoint; dimensions are bounded by the field's minimum and maximum.

| Block                | Additional controls                                                                                                                  |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Heading / Page title | `font_size_px`, unitless `line_height`, `color`; semantic `level` stays independent                                                  |
| Section              | `max_width_px` for the inner content, `content_gap_px`, `padding_x` (`auto`, `none`, `sm`, `md`, `lg`)                               |
| Container            | `max_width_px`, `gap_px`, `padding_x_px`, `padding_y_px`, `padding_top_px`, `padding_bottom_px`; opt-in `sticky` and `sticky_top_px` |
| Two columns          | `gap_px`, `right_width_px`; optional `stack_below` selects the shared column/outline boundary                                        |
| Site logo            | `height_px`, with intrinsic aspect ratio                                                                                             |
| Icon box             | `icon_size_px`, `heading_size_px`, `min_height_px`, `padding_px`, `radius_px`, `background`, `shadow: subtle`, `whole_card_link`     |
| Table of contents    | `padding_px`, `radius_px`, `border`, `shadow: subtle`, `link_color: neutral`, `list_style: chevron`                                  |
| Breadcrumbs          | `padding_before_px`, `padding_after_px`, `divider`                                                                                   |

For an edge-to-edge composition use a top-level Container with `width: full`,
`padding_x_px: 0`, `padding_y_px: 0` and `gap_px: 0`. Sections keep backgrounds
full width while `max_width_px` constrains their inner content. A 1140px inner
area with a 280px right column and 60px gap leaves 800px for the article when
space permits. Use smaller responsive gaps on narrow screens.

An Icon box with `whole_card_link: true` links its heading and stretches that
single link over the card. Body links remain independently accessible. Supply a
heading and link; an empty target never produces an empty anchor. In repeaters,
map the heading and link from the referenced Page so navigation follows its route.

Image blocks now explicitly reset their own image margin and `radius: none`.
Prose images retain their prose styles. Keep `fit: contain` and `aspect_ratio: auto`
to show the complete image; a crop remains an explicit editorial choice.

Set `settings.fonts.heading` and/or `settings.fonts.body` to `system` for the
visitor's native system font stack, with no Google Fonts request for that family.
This works identically in preview and static output. Other values remain Google
Fonts family names. Check geometry and keyboard focus at each relevant breakpoint
before publishing; precise dimensions cannot replace visual review.

Columns default to `stack_below: "721"` (the existing layout at 720px and below). Choose
`"768"`, `"1024"` or `"1280"` to stack below that viewport width. For example,
`"1024"` gives a single column at 768 and 1023px, then two columns at 1024px.
A Table of contents placed directly in a column slot follows this boundary:
`mobile_display: "hidden"` hides the outline and its otherwise empty slot;
`"visible"` keeps it in normal flow while stacked. Sticky behavior returns with
the two-column layout. An empty generated outline never reserves a spare track
or row; other sidebar blocks remain visible. Standalone outlines retain their
720px mobile behavior. Select the breakpoint from measured source/readability
needs, not solely from whether the layout overflows.

Container `padding_top_px` and `padding_bottom_px` independently override
`padding_y_px` (then the spacing token). All three accept breakpoint maps; zero
is a real value. For example, a hero can use top padding
`{ "mobile": 12, "tablet": 20, "laptop": 25 }` and bottom padding
`{ "mobile": 35, "tablet": 50, "laptop": 60 }` without spacer blocks.

Grid, Repeater and its aliases accept `gap_px` (0–240, responsive). This overrides
`gap` for that instance across grid, list, carousel and other repeater layouts.
For example `{ "mobile": 15, "tablet": 20, "laptop": 25 }` gives four 271.25px
cards in a 1160px desktop well. Nested layouts use their own settings.

For a persistent site header, make the header partial's outer Container a
`tag: "header"` with `sticky: true`. It stays in normal document flow until it
reaches `sticky_top_px` (default 0; optional responsive 0–240px) and uses stacking
level 100. Choose an opaque background. Keep it outside the article/main and
avoid a short enclosing wrapper or overflow-clipping ancestor: CSS sticky is
bounded by its containing block. Other Containers remain static by default.
The outline measures the actual sticky header for its top clearance and anchor
scroll margins. Its active-heading feedback also accounts for document
`scroll-padding-top`; remove obsolete tenant offsets when they duplicate the
native clearance, rather than adding another compensation.

Button `new_tab: true` opens its link in a new tab using native HTML
`target="_blank"` with `rel="noopener noreferrer"`, even without JavaScript.
Omitted or false keeps navigation in the same tab. Supply a JSON boolean, not a
string. Keep the label meaningful; long labels wrap within the available width.
During migration verify the rendered link's query parameters, fragment and tab
behavior. Source CTA classes copied into Prose do not recreate a Button. If the
source requires additional link semantics such as `sponsored`, `nofollow` or a
forced download, do not assume that `new_tab` preserves them; verify support in
the selected block before converting it.

## Block menus and article cards (next Core release)

`core/navigation_menu` provides two editable block slots: **Desktop / shared**
(slot 0) and optional **Mobile override** (slot 1). Leave slot 1 empty to reuse the
same content, or build a completely different mobile layout. Use shared partials
for reusable parts rather than copying link values. `core/navigation_links`
provides semantic link lists with color, text size, weight, spacing and direction;
combine them with native containers and headings. The same blocks work in footers.

`collapse_below` accepts `576`, `768`, `769`, `1024` or `never` (strings); default `1024`
means modal below 1024px and inline at 1024px and above. The modal preserves the
header position, locks background interaction, contains keyboard focus, closes on
Escape, link activation or desktop transition, and restores focus on dismissal.
Without JavaScript, the appropriate menu content remains available in the page.
The simpler `core/navigation` remains available for flat inline/disclosure menus.

```json
{
  "id": "main-menu",
  "type": "core/navigation_menu",
  "data": { "collapse_below": "768", "aria_label": "Main navigation" },
  "slots": [
    [
      {
        "id": "desktop-links",
        "type": "core/navigation_links",
        "data": {
          "direction": "row",
          "links": [{ "label": "Services", "href": "/services/" }]
        }
      }
    ],
    [
      {
        "id": "mobile-links",
        "type": "core/navigation_links",
        "data": {
          "font_size_px": 28,
          "color": "#075696",
          "links": [{ "label": "Explore services", "href": "/services/" }]
        }
      }
    ]
  ]
}
```

`core/post_card` retains natural image proportions by default. Set `image_fit:
"cover"` explicitly when cropping is intended. Optional responsive
`image_height_px`, `title_size_px`, `title_line_height`, `title_weight`,
`body_padding_px` and `radius_px` control article-card proportions. Set
`appearance: "card"` for a joined image and panel, and `shadow` to `default`,
`none` or `subtle`. `whole_card_link: true` creates one stretched title link when
there is no secondary action and the title and URL are present. A download or
separate page action disables that whole-card mode; anchors are never nested.

Horizontal cards use `layout: "row"` with `image_width_percent` (10–70, default 40).
Missing media leaves no empty image column. `action_label` adds a separate page
link, and `download_style: "outline"` presents the mapped download URL as a
bordered action. These controls work in standalone cards, page lists and repeaters.
`core/icon.size_px` provides a responsive numeric icon size.

Presentation field maps still use the standard breakpoints: tablet 640, laptop
1024, desktop 1280 and wide 1536px. A menu's `collapse_below` changes only its
behavior threshold, **not** those style buckets. Source layouts changing at
576/768px require an explicit capability gap or deliberate accepted mapping;
six sampled widths are not proof of all intermediate widths. Do not hide an
unsupported source breakpoint with undocumented CSS.

`template_content_slot.max_width: "full"` adds no implicit gutter when typography
is set. Narrow, normal and wide slots retain their declared content widths.
Nested page blocks remain responsible for their own spacing.

`collapse_below: "769"` keeps the mobile menu through 768px, then switches at
769px. `toggle_size_px` sizes the open/close icons independently of their minimum
44px hit area. Link groups accept `font: "body"` or `"heading"` to use the site's
font choices. Each link may include an `icon`; `icon_size_px` and `icon_gap_px`
separate its size and spacing from the label. SVG icons and emoji both honor
`core/icon.size_px`.

## Native presentation controls (Core 0.2.28)

Use typed block fields before writing corrective CSS. These controls work in
Page bodies, shared Page templates, partials and repeater item overrides.

- `core/prose`: `font_size_px`, `line_height`, `paragraph_spacing_px`, `text_align`
  and `font_weight` support responsive values; `font` selects `inherit`, `body`
  or `heading`. For footer copy, use `font_size_px: 14.4`, `line_height: 1.6`,
  `text_align: "center"` and `paragraph_spacing_px: 0` on ordinary prose.
- `core/container`: `min_height_px` supports responsive minimum height. Content
  may grow beyond it; this never clips longer translations or zoomed text.
- `core/post_card`: `actions_direction`, `actions_gap_px`, `action_size_px`,
  `action_weight` and `body_gap_px` control the action group and panel spacing.
  Keep the page and download destinations separate. `whole_card_link` is
  disabled when secondary actions are present.
- For an image-free link card, set `show_image: false`, `whole_card_link: true`,
  `title_icon: "arrow-right"`, and optionally `title_icon_color`,
  `title_icon_size_px` and `title_icon_gap_px`. The decorative icon stays inside
  the named title link; it does not add a second keyboard target.

Example Post Card data for a repeater with a public PDF field named `pdf`:

```json
{
  "layout": { "mobile": "column", "laptop": "row" },
  "image_width_percent": 40,
  "action_label": "Read",
  "download_url_field": "pdf",
  "download_style": "outline",
  "actions_direction": { "mobile": "column", "laptop": "row" },
  "actions_gap_px": 20,
  "action_size_px": 14.4,
  "body_gap_px": 20
}
```

Missing media is omitted. Action rows may wrap when space is limited. Cards
retain their data order; these fields do not sort the listing. See
[site-specific widths](/docs/tools/settings/#site-specific-responsive-widths-core-0228)
for exact authored breakpoints. Existing sites must be republished to use the
new renderer. Cloud and self-hosted installations need Core 0.2.28; MCP schemas
are available from 0.45.24.
