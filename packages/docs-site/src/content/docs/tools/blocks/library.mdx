## The block library

The AI agent calls `list_block_types` first to see the built-in and custom types available on the selected Site. Built-in type IDs are stable; custom types belong to a Site, and each placed block has a separate instance ID. The [catalog](../../../guides/block-library/) lists all 77 built-in types in Core 0.2.77. The sections below explain common groups and their settings:

### Layout primitives

- `core/section` — outer container with width + padding + bg
- `core/container` — flex container (direction / wrap / gap / align). With
  `layout: "flow"` it renders one plain element (`tag`: div, section, article,
  aside, nav, header, footer, main, figure or `a`) with your `css_class`. Set
  `tag: "a"` and `href` to make the whole container one link, such as a
  clickable card; only http(s), relative, `#`, `mailto:` and `tel:` targets are
  kept. `lang` (**Language of this part**) marks a part written in another
  language than the page; see
  [a part of a page in another language](#a-part-of-a-page-in-another-language).
- `core/grid` — N-column grid that wraps automatically
- `core/columns` — 2-slot Left/Right container for asymmetric layouts
- `core/spacer`, `core/divider`

### Content + marketing

- `core/heading`, `core/prose`, `core/button`, `core/image`, `core/icon`, `core/icon_box`
- `core/hero` (4 layout variants), `core/cta`, `core/feature_row` (gutter-hugging image + text row)
- `core/accordion`, `core/tabs`, `core/video`, `core/form`, `core/media_card`
  - `core/accordion`: when every item's title ends with a question mark and has an
    answer, the page publishes `FAQPage` structured data from the accordion; see
    [FAQ from accordions](../../../technical/seo-and-indexing/#faq-from-accordions).
- `core/search` — see [Site search](#site-search) below
- `core/html` — the raw-HTML escape hatch for one-offs no block covers. Output is sanitised the same way HTML-mode pages are, so it isn't a script vector.

### Video, hero video and ratings (render version 7)

From [render version 7](../../settings/#render-versions) these
options render; earlier versions ignore them.

- `core/video`: a YouTube or Vimeo page address (`watch?v=`, `youtu.be/`,
  `shorts/`, `vimeo.com/123`) becomes the provider's embed address, YouTube on
  its no-cookie host. With `source: "url"` a video file plays in the browser's
  own player. `poster` (files), `autoplay` (always muted), `loop`, `muted`
  (files; embeds start muted only when autoplaying), `controls` and
  `lazy_load` apply, and `title` (default "Video") names the player for
  screen readers. Embeds are limited to the iframe host allowlist.
- `core/hero`: `video_url` with a video file plays muted and looping behind
  the text, with `image` as its poster, a pause button, and nothing at all when
  the visitor prefers reduced motion. YouTube and Vimeo addresses are not used
  as background video.
- `core/testimonial`: `rating` (0–5) shows as whole stars with "Rating: 4 out
  of 5" ("Betyg: 4 av 5" on Swedish sites) for screen readers. Set
  `--testimonial-rating-color` to change the star colour.

### Motion, background media and story blocks (render version 14)

From [render version 14](../../settings/#render-versions):

- **Entrance animation.** `motion` on sections, containers, grids, columns,
  lists (gallery, logo cloud, feature grid, testimonials, team, pricing) and
  hero, CTA, feature row, media card, image, heading, video, key figures,
  timeline, audio and before/after: `none` (default), `fade`, `rise`, `scale`
  or `custom`. It plays once as the block scrolls in. A container, grid or list
  brings in its blocks one after another; a hero or CTA moves its text, not its
  background. What is on screen when the page opens stays still. Without
  script, in print and for visitors who prefer reduced motion everything is
  simply there.
- **Background media.** A section takes `background_image` (with
  `background_focal_x` and `background_focal_y`) and sections, containers and
  CTAs take `background_video`, a muted looping MP4 or WebM file (YouTube and
  Vimeo are not backgrounds). The video starts when the block is in view,
  pauses out of view, has a pause button, and shows the image on phones unless
  `background_video_phones` is `play`. `background_overlay` (0–100, default 40) darkens the media so white text reads; set a text color, or 0, for text
  in your own color.
- **Text over images.** On hero, section and CTA:
  - `overlay_style`: `solid` (even), `gradient` (from `overlay_side`: bottom,
    top, left or right) or `spot` (a soft darkening behind the text), in
    `overlay_color` (default black), over a background image or video alike;
    a container takes these three too, without a text plate;
  - `text_panel`: a plate behind the text: `solid` (page colors),
    `dark_translucent`, `light_translucent`, `dark_glass` or `light_glass`
    (blurs the image behind the text) or `band` (full width);
  - `text_panel_shape`: `rounded`, `square`, `pill`, `blob` (organic),
    `slant` or `custom`;
  - on a section, `text_position` (nine places, per screen size) and
    `min_height` (`sm`, `md`, `lg`, `screen`). The text keeps to the content
    column of the sections around it. A hero places its text with
    `text_vertical` and `text_align` as before.
- **Video in several sizes and formats.** `core/video` (with `source: "url"`)
  takes `sources`, a list of `{ src, width, type }` (MP4 and WebM in several
  widths); the browser picks the smallest that is sharp on the screen. Sections,
  containers and CTAs take `background_video_sources` the same way, and the
  background plays the smallest playable file at least as wide as the block.
  The media library accepts MP4 and WebM video up to 25 MB per file.
- **Gallery lightbox.** `core/gallery` opens images that have no link larger,
  with previous and next, the arrow keys, swiping and Escape; `lightbox: false`
  turns it off.
- **Moving logo row.** `core/logo_cloud` with `layout: "marquee"` scrolls
  slowly sideways, pauses on hover, focus and its pause button, and is a still
  row without script or with reduced motion.
- **Site setting** `motion: "reduced"` turns all of this motion off for every
  visitor, and the hero video and carousel autoplay too.

New blocks (any render version):

- `core/stats` (key figures): a figure, label and optional description per
  item, up to `cols` per row, `plain`, `cards` or `divided`. Numbers count up
  once as they scroll in (`count_up`); the final figure is in the page.
- `core/timeline`: date, title, text and an optional image per event, as one
  line or alternating sides on wide screens.
- `core/audio`: an audio file with title, description, cover and a
  transcript link.
- `core/before_after`: two images with a draggable, keyboard-operable divider;
  side by side without script.
- `core/announcement_bar`: a short message with a link, in primary, surface or
  dark colors. Visitors can close it; it stays closed in that browser until the
  message changes. Put it at the top of the header template.
- `core/scroll_steps`: steps that scroll past a picture that stays in place
  and changes with the step. On phones, without script and in narrow columns,
  each step shows its picture above its text.
- `core/scroll_film`: a film that plays frame by frame as the page scrolls,
  with captions that show between two points of the film (`start`, `end` in
  percent). Give the frames as an address pattern (`frames_pattern` such as
  `/media/film/frame-{nnnn}.webp` with `frame_count`, optionally a phone
  pattern) or a list (`frames`, with `frames_phone` for phones), or a `video` file. Frames are smoothest:
  export 60–200 WebP or AVIF frames about 1600–2000 px wide. A video plays
  smoothly when every frame is a keyframe. Without script and for reduced
  motion the block is its still image (`poster`, or the first frame) followed
  by the captions.

- `core/svg_animation`: an SVG drawing (`svg`, pasted markup; scripts and
  event attributes are removed) that animates. `effect`: `draw` (all lines
  together), `draw_sequence` (one line after another), `reveal` (the
  drawing's top-level parts appear in turn) or `custom` (only the progress,
  for your own CSS). `trigger`: when it scrolls into view (once or every
  time), when the page opens, when its top reaches `position` % of the
  screen, scrubbed by scrolling (finished at `position`), or a loop with a
  pause button and `loop_pause` between rounds. `label` names the drawing
  for screen readers; without one it is decorative. Without script and for
  reduced motion the finished drawing shows.

(`style_overrides.custom_css`) and the scripts of your own block types:

| `[data-motion-in]` and `motion: "custom"`                                                                        | each element that enters | your own animation: `html[data-tr-motion] [data-motion-item="custom"]:not([data-motion-in]) { … }` (the `html[data-tr-motion]` part keeps content visible without script) |

`@media (prefers-reduced-motion: no-preference)`.

### Article content and automatic contents

Use `core/table`, `core/list`, `core/image`, `core/video` and formatted headings
for editable article content. Tables support header cells, spans, colors,
column widths and horizontal scrolling. Images support original dimensions,
alignment, a separate mobile image, a link and formatted photo credits.

The mobile image (`mobile_src`) replaces the main image below 640px. To switch
at another width, set `mobile_src_below` to a breakpoint (`tablet`, `laptop`,
`desktop` or `wide`). The width comes from the block's `responsive_breakpoints`,
else the Site's. For example, `laptop` with a laptop width of 768px shows the
mobile image up to 767px. `mobile_src_below_px` sets an exact width instead
(320–2560) and takes precedence. Existing images without either field keep the
640px switch.

An image with a `link` can also set `link_rel`, a space-separated list of link
relationships such as `nofollow sponsored`, and `new_tab: true` to open the link
in a new tab. A new tab always adds `noopener noreferrer`. Tokens other than
plain names are ignored. Images without these fields render as before.

Place **`core/table_of_contents` in the Page template**, next to its
`template_content_slot`. It derives links from the current Page's headings;
there is no editable list or source content field. Choose `h2`, `h2-h3` or
`h2-h4`. Changing, moving or removing a heading updates the generated list.
Existing heading anchors are preserved and links are present without JavaScript.
You can choose a plain list or card, indentation, desktop stickiness and
highlighting of the current heading. On mobile it stays in normal document flow.
The same block also works inside a Page body.

The Article template starter places its table of contents beside the body on
larger screens and before the body on mobile. The Two columns block's **Mobile
order** setting controls this order independently of the desktop layout.

### One main heading and mobile defaults

A Page template that provides an H1 (usually **Page title**)
owns the Page's main heading. Use H2 for headings in the Page body. The editor's
Save action and API writes reject a body H1 that duplicates the template title,
with an explanation of how to fix it. A Page without a template H1 can keep its
own body H1. HTML-mode Pages also allow only one H1.

Existing content remains editable: preview and static builds render additional
body H1 headings as H2, preserving their text and anchors. A known template H1
always takes precedence. The layout does not add another automatic Page title.
This safeguard does not rewrite saved content; correct the heading level before
saving a changed body. Custom header/footer HTML should use a non-heading element
for the site brand.

A header, footer or menu partial renders before every Page's H1, so a label in
it, such as "Get a quote:" above contact links in a mobile menu, is not a
heading. Use `core/prose` with a paragraph and set its size, weight and colour:

```json
{
  "type": "core/prose",
  "data": {
    "html": "<p>Get a quote:</p>",
    "font_size_px": 18,
    "font_weight": "700",
    "color": "on_secondary"
  }
}
```

`color` on `core/prose` and `core/text` takes the same values as the heading's
`color`: a palette token (`text`, `primary`, `on_secondary`, …), a palette CSS
variable or an explicit CSS colour. It is set on the block element, so it wins
over the colour of the block's style; links and headings inside keep their own
colours. Without it the output is unchanged on every render version.

Repeater grids, including **Page list**, show one column below **768 px** by
default. Set **Mobile columns** (`mobile_cols`, 1–6) only when multiple columns are
intentional. An explicitly authored `cols.mobile` is also respected;
`mobile_cols` takes precedence. At 768 px and wider, the normal `cols` settings
apply. This listing-specific threshold does not change the general responsive
breakpoints used by other blocks. Masonry remains an explicit layout choice.

The default content gutter is **1.25 rem** below 768 px and **1.75 rem** above it.
Full-width section backgrounds still reach the viewport edges, while their
content has the same gutter. Site CSS can customize `--content-gutter`.
These shared defaults apply to both Cloud and self-hosted sites after upgrading
Core and rebuilding the site; previously published files remain unchanged.

otherwise the site `language`). The primary subtag decides, so `fr-FR` and
`fr-CA` both read as `fr` and `pt-BR` as `pt`; Chinese also reads the script or
region. Every surface below has built-in wording in these 50 languages:
Swedish (`sv`), Norwegian Bokmål (`nb`, `no`), Danish (`da`), German (`de`),
Dutch (`nl`), Finnish (`fi`), French (`fr`), Polish (`pl`), Italian (`it`),
Spanish (`es`), Portuguese (`pt`), Russian (`ru`), Ukrainian (`uk`), Czech
(`cs`), Slovak (`sk`), Hungarian (`hu`), Romanian (`ro`), Bulgarian (`bg`),
Croatian (`hr`), Serbian (`sr`, Cyrillic), Bosnian (`bs`), Slovenian (`sl`),
Macedonian (`mk`), Albanian (`sq`), Greek (`el`), Lithuanian (`lt`), Latvian
(`lv`), Estonian (`et`), Icelandic (`is`), Turkish (`tr`), Azerbaijani (`az`),
Kazakh (`kk`), Georgian (`ka`), Arabic (`ar`), Hebrew (`he`, `iw`), Persian
(`fa`), Urdu (`ur`), Hindi (`hi`), Bengali (`bn`), Tamil (`ta`), Thai (`th`),
Vietnamese (`vi`), Indonesian (`id`, `in`), Malay (`ms`), Japanese (`ja`),
Korean (`ko`), Chinese Simplified (`zh`, `zh-CN`, `zh-Hans`), Chinese
Traditional (`zh-Hant`, `zh-TW`, `zh-HK`, `zh-MO`), Catalan (`ca`) and English
(`en`):

Serbian wording is in Cyrillic; a site in Latin-script Serbian can write its own labels. Other languages, such as Welsh or Swahili, use English. A publication for such a language lists the

own texts, always win.

#### Right-to-left languages

Pages in a right-to-left language (Arabic, Hebrew, Persian, Urdu, Pashto,
Sindhi, Uyghur, Yiddish, Dhivehi and Kurdish Sorani, or any tag with an Arabic
or Hebrew script subtag such as `az-Arab`) get `<html dir="rtl">` automatically,
and the built-in layout mirrors: list and quote indents, table-of-contents
indents and chevrons, feature-row gutters, page navigation, form toggles,
carousel arrows and keys, tab arrow keys and the cookie button move to the other
side. Sides you choose yourself, such as image, divider and caption alignment,
stay as chosen. Left-to-right pages are unchanged.

#### A part of a page in another language

When one part of a page is in another language, such as a French column on a
Dutch (`nl-BE`) page, put that part in a **Container** (`core/container`) and
set its `lang` (**Language of this part**) to a BCP 47 tag such as `fr-BE`:

```json
{ "type": "core/container", "data": { "lang": "fr-BE" }, "children": [ ... ] }
```

The container's element gets `lang="fr-BE"` in the published HTML and in
preview, so screen readers read every heading, text, button and image
description inside it in French. The tag is checked like a language section's:
a primary language with an optional script and region (`fr`, `fr-BE`,
`zh-Hant-TW`), stored in canonical casing. Another value is rejected when the
block is written. Leave `lang` empty to use the page language; the container's
markup is then unchanged.

A right-to-left part (`ar`, `he`, `fa`, …) also gets `dir="rtl"`, and a
left-to-right part on a right-to-left page gets `dir="ltr"`. A `dir` you set
under **Additional attributes** is kept, and `lang` wins over a `lang` written
there. The mirrored layout of right-to-left pages follows the page language,
not the part. Use a container for a whole part; for a few words inside a
paragraph, `<span lang="fr-BE">` in `core/prose` still works.

### Structured Page fields without empty labels

**Requires template capability `supports_page_field_list`.**
Cloud and self-hosting use the same block; check the deployed site's capabilities
before adding it.

Add **Page field list** (`core/field_list`) to a Page template to present typed
values from the current Page's `fields`. Rows use a 0.7 rem vertical gap, labels use
font weight 600, and long values wrap to avoid horizontal overflow. Choose the content type's field names;
leave each label blank to use its schema label. Values stay in the structured
field editor. Changing and saving a Page field updates preview and the next
publication without editing the Page body or copying values into rich text.

```json
{
  "id": "facts",
  "type": "core/field_list",
  "data": {
    "title": "At a glance",
    "layout": "two-column",
    "fields": [
      { "field": "website" },
      { "field": "headquarters", "label": "Based in" },
      { "field": "shipping" },
      { "field": "regions" }
    ]
  }
}
```

The example assumes those fields are declared on the Page's content type.
The block renders a semantic definition list. `stack` is the default layout;
`two-column` becomes a single column on small screens. The optional heading is
an H2. Use multiple field-list blocks for independently titled sections.

- Null, missing values, blank strings (including whitespace), and empty lists
  omit the **whole row**, including its label.
- If no rows remain, the **whole block and its heading** are omitted from HTML.
- Number `0` is a value. Boolean rows default to
  `boolean_display: "property"`: show **Yes** for true and hide false/unset.
  Choose `boolean_display: "yes-no"` to show both set values. `true_label` and
  `false_label` let you use labels such as **Ja** / **Nej**. This changes
  presentation only; false remains a stored value.
- Text and textarea values are escaped. URLs become HTTP(S) or site-relative
  links; unsafe URLs are omitted.
- Select and multiselect fields use `option_labels` when configured, falling
  back to the stored option. Multiselect values render as a list.
- `page_ref` and `page_ref_list` resolve to Page titles and links. Missing,
  unpublished, unlisted or unrouted targets are omitted. Lists preserve the
  selected order without duplicate links.
- Unknown fields, unsupported field types, and fields with **`rendered: false`**
  never render. A private field cannot be exposed by selecting or styling it.

#### Fine-tune an individual row

Each row optionally accepts `html`, `css` and `css_class`. For example:

```json
{
  "field": "shipping",
  "html": "<dt>{{label}}</dt><dd><span class=\"badge\">{{value}}</span></dd>",
  "css": "padding: 0.75rem; background: #f3f6fa; border-radius: 0.5rem;",
  "css_class": "shipping-fact"
}
```

`html` replaces the contents of that row's wrapper. Keep a `dt` label and `dd`
value for definition-list semantics. Its only slots are `{{label}}` (escaped
label) and `{{value}}` (the safely formatted value, including links or lists).
Place the value slot in element content. No Page expressions or conditionals are
evaluated, and values are never reinterpreted as template code. Custom markup
passes through the normal HTML sanitizer; it cannot add scripts or event handlers.

`css` contains CSS declarations applied to that row's wrapper. For more detailed
selectors, give the row a `css_class` and use the block's existing **Custom CSS**
setting, for example `.shipping-fact .badge { font-weight: 600; }`.
Empty and private fields are omitted **before** custom row markup or styles are
applied; a custom label or placeholder cannot make an empty row visible.

#### Checkbox lists with icons and selected links

A multiselect already renders one selected option per list item. Set
`item_html` on that field's row to customize each selected option. For example:

```json
{
  "field": "delivery_methods",
  "css_class": "delivery-options",
  "item_html": "<span class=\"checked-box\" aria-hidden=\"true\">☑</span> <span>{{value}}</span>",
  "item_links": [{ "value": "local_pickup", "url": "/delivery/local-pickup/" }]
}
```

If `local_pickup` has the schema label **Local pickup**, the visitor sees that
label as a link; other selected options remain plain labels. `item_links`
uses stored option values for matching. Unsafe link URLs are ignored. You can
use a custom image inside `item_html` instead of the checkbox character.

Use the block's Custom CSS for the list and icon, for example:

```css
.delivery-options .field-list-values {
  list-style: none;
  padding: 0;
}
.delivery-options li {
  display: flex;
  align-items: baseline;
  gap: 0.5rem;
}
.delivery-options .checked-box {
  color: #087044;
}
```

Within `item_html`, `{{value}}` is the formatted option label (including its
configured link) and `{{label}}` is the plain escaped option label. The same
item template can decorate Page references; their links still come from the
referenced Pages rather than `item_links`. Unselected options never render;
clearing the field removes the entire row, including its heading and icons.
This is presentation stored once in the Page template, not copied Page content.

Agents use the existing `list_block_types`, `read_block_type` and `add_block`
tools with `target: { "kind": "template", "id": "profile" }`. Inspect the content
type first. Do not generate per-Page facts HTML or a duplicate rich-text field.

### Typography in a Page template

Select the template's **Page content** block to set
**Body text size (px)**, **Body line height**, and **Paragraph spacing (em)**.
For example, 16 px with a line height of 1.6 produces 25.6 px lines. Leave a
field empty to keep the block defaults. The settings apply inside that content
slot; navigation, related cards and other template content keep their own styles.
They do not change the saved text or require custom CSS.

### Related Pages

For a curated list, use `core/repeater` with **Source: Pages** and select Pages
in the desired order. Leave Content type empty to combine articles, checklists
and other types. **Exclude current Page** removes the page being displayed.
Missing and unpublished pages are omitted before the item limit is applied.

In a shared Page template, use **Source: Related** and name a Page reference
field from the Content type. Each Page then supplies its own selection, while
the template owns the card layout. Use **Backlinks** to list pages referring to
the current Page. `core/post_card` provides the image, title and link presentation.

### Item-compatible kernels

Designed to tile cleanly inside a repeater — no outer padding, kernel layout. Render fine standalone too.

- `core/testimonial`, `core/team_member`, `core/pricing_plan`, `core/post_card`, `core/logo_item`, `core/step_card`

### Repeater + aliases

The repeater abstraction collapses what used to be a dozen specialised widgets into one primitive. The aliases are author-friendly wrappers:

- `core/gallery` — image grid
- `core/logo_cloud` — client logos (greyscale by default)
- `core/testimonials` — testimonial carousel

From render version 7, a repeater with `layout: "carousel"` (testimonials by
default) has previous and next buttons (`show_arrows`), a dot per item
(`show_dots`) and, with `autoplay: true`, advances every 5 seconds with a pause
button. Autoplay stops while the visitor points at or focuses the carousel and
never runs when they prefer reduced motion. Items scroll in a track inside the
block; without JavaScript the track still scrolls and the controls stay
hidden. The controls name themselves in the site language. Styles reach them
as the repeater's parts `carousel_controls`, `carousel_button` and
`carousel_dot` (an alias's carousel shares them: `core/repeater.carousel_dot`);
the current dot is `&[aria-current="true"]` in the dot style's advanced CSS.

Grouped and paginated repeaters render their group titles and archive pager
next to the repeater element, where parts do not reach, so each has a style
field: `group_title_style_id` (a heading style on every group title) and
`pager_link_style_id` (a button style on every page link and the current page,
`&[aria-current="page"]` for the current one).

- `core/feature_grid` — icon_box grid
- `core/pricing_table` — pricing_plan grid
- `core/team_grid` — team_member grid
- `core/page_list` — Pages of any content type, items become post_cards

The static aliases accept `items: [{...}]`: pass the per-item field values and the renderer expands the alias to a repeater with the right item block. `core/page_list` instead queries saved Pages using `content_type` and its query settings; it does not take a hand-maintained array of article data.

Frozen publications retain static rows against the selected item
block’s public schema, including card field mappings and grouping labels.
`rendered: false` fields and unrelated row metadata stay private. A Post Card row
can use `{ title: "Guide", href: "/guide/" }`; use `item_overrides` for shared
presentation. Republish sites built with an older Core to restore missing static
card values. Saved CMS rows do not need to be rewritten.

```
"Add a feature grid with our three differentiators."
  → add_block block={type:"core/feature_grid", data:{items:[
       {icon:"zap", heading:"Fast", text:"<p>...</p>"},
       {icon:"shield", heading:"Safe", text:"<p>...</p>"},
       {icon:"smile", heading:"Simple", text:"<p>...</p>"}
     ]}}
```

From render version 16, `last_row: "center"` on a grid repeater (and on
`core/feature_grid`, `core/team_grid`, `core/pricing_table` and a grid of
`core/testimonials`) puts a short last row in the middle, for example one card
under a row of three. The items keep equal widths from `cols` (and
`mobile_cols` on phones). Unset, the last row starts at the left. A logo grid
(`core/logo_cloud`) already centres its last row from version 16;
`last_row: "start"` turns that off, and `logo_height_px` sets the height of
its logos.

### Template/\* family (dynamic context)

These read from the render context (`page`/`site`/`item`) rather than from authored block data. Used inside Page templates so a blog template can render every post with its own title without per-post copy.

- Page-context: `template/page_title`, `template/page_featured_image`, `template/page_excerpt`, `template/page_date`, `template/page_author`, `template/page_breadcrumbs`
- Site-context: `template/site_logo`, `template/site_title`, `template/site_tagline`
- Item-context: `template/page_title`, `template_content_slot`, `template/page_featured_image`
- Conditional: `template/show_if` (renders children only if a condition is truthy)

Several template blocks render with the markup of the block they stand in for,
so they share its CSS. From render version 16 each of them also carries its own
`data-template-block` attribute on the block element, so site CSS can tell
them apart. (`data-template` on `<body>` is something else: the page's Page
template id.)

| Template block                 | `data-block`      | `data-template-block` (render version 16) |
| ------------------------------ | ----------------- | ----------------------------------------- |
| `template/page_title`          | `heading`         | `page_title`                              |
| `template/site_title`          | `heading`         | `site_title`                              |
| `template/page_featured_image` | `image`           | `page_featured_image`                     |
| `template/page_excerpt`        | `prose`           | `page_excerpt`                            |
| `template/site_tagline`        | `prose`           | `site_tagline`                            |
| `template/page_date`           | `page-date`       | —                                         |
| `template/page_author`         | `page-author`     | —                                         |
| `template/page_breadcrumbs`    | `breadcrumbs`     | —                                         |
| `template/site_logo`           | `site-logo`       | —                                         |
| `template/page_navigation`     | `page_navigation` | —                                         |

```css
[data-block="heading"][data-template-block="site_title"] .block-heading-text {
  letter-spacing: 0.02em;
}
```

Render version 16 also adds settings to these blocks:

- `template/site_title`: `align` (`match-parent`, the default, keeps the
  alignment of the text around it; `left`, `center`, `right`) and
  `link_to_home` (links the name to the home page of the page's language).
- `template/page_excerpt` and `template/site_tagline`: `font_size_px`,
  `text_align` (`inherit`, `start`, `center`, `end`, `justify`) and `color`, as
  on a Text block.
- `template/page_featured_image`: `align` (`left`, `center`, `right`),
  `radius` (`none`, `md`, `lg`, `xl`) and `focal_x` / `focal_y`, as on an Image
  block. Its rules apply to the featured image only (before, they also styled
  every Image block on the page), and its `width` applies whether or not the
  page has an Image block. The `image` part styles the image.
- `template/site_logo`: the small height (`height: "sm"`) is 2rem instead of
  1.5rem, so a logo with a wordmark or tagline stays readable.
- `template/page_navigation`: the labels and titles have the classes
  `page-navigation-label` and `page-navigation-title`.

### Page featured image

`template/page_featured_image` shows the page field named by `field` (default
`og_image`) and renders nothing when the page has no image. From Core 0.3.31
it also takes these settings, on every render version:

- `alt_field`: the page field with the image's alt text, for example
  `featured_image_alt`. Empty, the alt text is the page title. From render
  version 21, a block without `alt_field` uses the field named after the image
  field with `_alt` added (`featured_image_alt` for `featured_image`) when it
  has a value, and the page title otherwise.
- `loading`: `auto` (the default) marks the image lazy, and the published site
  loads the page's first image immediately with high priority, so a featured
  image at the top of the page is loaded first anyway. `eager` always loads it
  immediately with `fetchpriority="high"`; `lazy` never does.
- `aspect_ratio` per screen width, as on an Image block (for example
  `{"mobile": "16:9", "laptop": "3:1"}`), and the ratio `21:9`.
- `max_height_px` (80–2400, per screen width): the image keeps its width and is
  at most this high; with `fit: "cover"` it is cropped around the focal point.
- `mobile_field`: another page field with an image for small screens, with
  `mobile_src_below` / `mobile_src_below_px` as on an Image block's mobile
  image. `focal_x` and `focal_y` can also be set per screen width.

The image's `sizes` follows `width`: `narrow`, `normal` and `wide` are at most
512, 768 and 1024 px wide, and `full` follows the layout around it. The
published site gives the image the same `<picture>` with AVIF and WebP sources
as an Image block; previews show the original file.

A full-width featured image that stays low on a computer and 16:9 on a phone:

```json
{
  "field": "featured_image",
  "alt_field": "featured_image_alt",
  "width": "full",
  "fit": "cover",
  "aspect_ratio": { "mobile": "16:9", "laptop": "3:1" }
}
```

`"max_height_px": 300` with `"aspect_ratio": "16:9"` gives the same on wide
screens and keeps 16:9 where that is lower than 300 px.

### Site fields on pages

[Site fields](../../site-fields/) are values the client keeps on settings
pages: a phone number, a booking toggle, the opening hours. Pages, templates,
headers and footers show them in three ways, in every render version:

- `{{site.fields.name}}` in a block type's template, escaped like any text
  (`{{{site.fields.intro}}}` inserts rich text, cleaned like the rest of the
  page). A dot reads inside a group (`{{site.fields.address.city}}`), and
  `{{#each site.fields.staff}}…{{/each}}` repeats over a list. A whole block
  field can be bound too, for example a Text line with
  `text: "{{site.fields.phone}}"`. A token inside other text stays as written.
- `core/site_field` (**Site field**) shows one value. `field` names it, with
  dots for a value inside a group or list (`address.city`, `staff.0.name`).
  `format`:
  - `auto` (default) follows the field: rich text, numbers and dates in the
    page language, option labels for a dropdown, links for an address, email
    or page reference, a list for a list, and the week for opening hours;
  - `text`, `richtext`, `number`, `date` and `list` choose one;
  - `opening_hours_week`: a table of this week, Monday first, with weekday
    names in the page language and today's row marked (`data-today`,
    `aria-current="date"`). A day with a break reads "09:00–12:00,
    13:00–17:00". A date exception this week, such as a holiday, marks its
    row (`data-exception`) and shows its hours or "Closed", with its comment
    ("Julafton") in bold under the weekday name in the row header; a
    weekday's own comment ("Lunch closed 12–13") shows there in normal weight.
    The field's comment under the hours follows the table;
  - `opening_hours_today`: today's hours ("09:00–17:00", or "Closed"); on a
    date exception with a comment, "Today · **Julafton**: Closed";
  - `next_opening`: "Opens tomorrow 09:00", or "Open now, until 17:00" while
    it is open, "Closed, opens again 13:00" during a break, and
    "Opens Friday (**Juldagen**) 10:00" when that day's exception has a comment;
  - `open_now`: "Open now, until 17:00" (until the break, before one), "Closed,
    opens again 13:00" during a break, or "Closed"; on a date exception with a
    comment, the comment comes first in bold.

  `label` is shown before the value (the week's caption), `empty_text` when
  the field is empty; without it an empty field renders nothing. `tag` is
  `p`, `span` or `div`; the week, lists and rich text use `div`. Parts:
  `label`, `value`, and for the week `day`, `hours`, `today`, `exception`
  (a row with other hours), `note` (a day's comment) and `hours_note` (the
  comment under the hours).

  A field its definition marks `live` (see [live site fields](../../site-fields/))
  also updates in the browser on a site that has live files: the block names
  the site's `_fields.json` (`data-site-field`, `data-site-field-src`) and a
  small script reads it once when the page opens and shows the newest value,
  formatted exactly as the publication would. This covers the formats
  `text`, `number`, `date` and the opening-hours formats; rich text, lists,
  page references and groups show the published value until the next
  publication. A live field that is empty at publication keeps a hidden place
  for its value. A failed request, or a field the file does not list, keeps
  the published value.

- `core/show_if` (**Show if**) shows the blocks inside it only when its
  `condition` holds: `site.fields.show_booking` (a ticked checkbox),
  `!site.fields.closed`, `site.fields.season === "winter"`, combined with `&&`
  and `||`. It reads page values too (`page.language === "en"`), like
  `template/show_if`. A condition that cannot be read hides the blocks.

```json
{
  "type": "core/show_if",
  "data": { "condition": "site.fields.show_booking" },
  "children": [
    {
      "type": "core/site_field",
      "data": { "field": "opening_hours", "format": "next_opening" }
    }
  ]
}
```

Opening hours use the site's time zone: its `time_zone` setting, otherwise the
usual zone for the site language (Swedish Europe/Stockholm, Norwegian
Europe/Oslo, Danish Europe/Copenhagen, Finnish Europe/Helsinki, British
English Europe/London and so on), otherwise Europe/Stockholm. The hours you
type are never converted; the zone only decides which day and hour it is. The hours depending on the day are computed when the site is
published and refreshed in the visitor's browser, so a page published on
Monday shows Tuesday's hours on Tuesday without a new publication. A small
script ships only on pages that show such a format; without script the
published value shows. Other values change with the next publication. Fields
a builder marks as not rendered never reach the published site, and a
publication lists blocks that read a field the site does not define in its
job `warnings`.

### Live snippets

`core/snippet` (**Live snippet**) shows one of the site's
[live snippets](../../snippets/): content kept outside the publication, such
as today's lunch, that editors, agents and apps change without publishing.

- `snippet` is the snippet's id.
- The block shows the content as of the publication, so it is there without
  script, for search engines and in print. For a dated snippet that is the
  entry of the publication date in the site's time zone (a date wins over its
  weekday, then the fallback). HTML is cleaned like the rest of the page;
  text is shown as text, line breaks kept.
- `live` (default on): on a site with live files the block also names the
  snippet's file (`data-snippet-src`), and a small script fetches it when the
  page opens, shows the newest content and chooses today's entry in the
  visitor's browser. HTML from the file is cleaned again in the browser to the
  tags of rich text (paragraphs, headings h2–h6, lists, quotes, emphasis,
  links to web, email and phone addresses, and images). A dated snippet is
  checked again at midnight while the page stays open, and every snippet
  after the page was hidden for ten minutes or more. A failed request keeps
  the published content. Off shows the published content only. The script
  ships only on pages with a live snippet, and only for a site with live
  files; on others the block shows the published content.
- `empty_text` shows when the snippet has nothing today; without it the block
  is hidden (`hidden`) and keeps its place for the browser to fill.
- `tag` is `div` (default), `section`, `aside`, `p` or `span`. Use `div`,
  `section` or `aside` for HTML with paragraphs or lists.
- The block carries `data-snippet`, `data-format`, `data-updated` (when the
  content was last written) and, for dated snippets, `data-snippet-date` (the
  day it shows). Updates are not announced to screen readers: they happen
  only right after the page opens and at midnight, never in response to the
  visitor, so an announcement would only interrupt.

```json
{
  "type": "core/snippet",
  "data": {
    "snippet": "lunch",
    "tag": "section",
    "empty_text": "No lunch today"
  }
}
```

A publication lists blocks that name a snippet the site does not have in its
job `warnings`.

## Site search

Add `core/search` to a page and your published site gets working full-text
search. There is nothing to configure and no third-party service involved:

```
Add a search box to the header.
```

At deploy time, if any page uses the block, the built HTML is indexed with
[Pagefind](https://pagefind.app/) and the index ships as static files alongside
the site. Search runs entirely in the visitor's browser against that index — no
search server, no per-query cost, and it works on any static host.

Sites without the block skip the indexing step entirely, so adding search costs
build time only when you actually use it.

The only field is `placeholder`. The result UI inherits your site's colours
through the same CSS variables as everything else.
